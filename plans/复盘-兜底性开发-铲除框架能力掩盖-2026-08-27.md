## 一、现状：问题定义

### 1.1 触发事件

2026-08-27，用户在群聊发「早上好」无人响应，给可灵私聊发「早上好」也无响应。

### 1.2 排查结论（已实测验证）

| 验证项 | 结果 |
|--------|------|
| 后端健康 | ✅ 正常（3 agents，Real mode qwen3.7-flash） |
| 私聊 WS（直连 + 经 Nginx） | ✅ 可灵正常回复 |
| 前端私聊 | ✅ 可灵正常回复 |
| **群聊 WS** | ❌ 发「早上好」后 57s 小码才回复，114s 可灵才回复，206s 超时小研没回复 |
| 后端日志 | ⚠️ `group run finished`（4 条消息）+ 大量 `send_json error` |
| 模型绑定 | 可灵绑定 mimo-v2.5（推理模型，响应慢），小研小码用默认 qwen3.7-flash |
| mimo-v2.5 实测 | ⚠️ 推理模型：reasoning_tokens 占 73%，单次响应 5.4s |

### 1.3 表面根因 vs 真正根因

**表面根因**：群聊用串行 SelectorGroupChat，无 @ 时 LLM 自动选人，每个成员发言间隔 ~57s，整个群聊跑完 200+ 秒，用户等不及刷新页面 → WS 断开 → 消息发不出去。

**真正根因（设计问题）**：**群聊引擎选错了模式**。用户要的是「三个独立的人各自回应」（并行独立），当前实现却是「一个人分饰三角的串行讨论」（共享对话流）。这不是换模型能解决的——换快模型深度不够，换慢模型太慢，这是 trade-off，不是解法。

## 二、根因分析：为什么会出现「兜底性开发」

### 2.1 框架能力盘点（已实测 autogen-agentchat 0.7.5）

```
autogen_agentchat.teams 导出：
├── SelectorGroupChat      → LLM 选人串行讨论（我们现在用的）
├── RoundRobinGroupChat    → 轮流发言（串行）
├── Swarm                  → Handoff 移交（串行）
├── MagenticOneGroupChat   → 编排器协调（串行）
├── GraphFlow              → ⭐ 图流编排（实验性）——支持并行 fan-out / join！
└── DiGraph / DiGraphBuilder → GraphFlow 的图构建 API
```

**GraphFlow 官方文档原话**：
> This group chat executes agents based on a directed graph structure, allowing complex workflows such as **sequential execution, parallel fan-out, conditional branching, join patterns**, and loops.

**DiGraphBuilder 并行 API**：
```python
add_node(agent, activation='all' | 'any')   # 节点激活条件
add_edge(source, target, activation_group=..., activation_condition=...)  # 边支持并行组
```

**已实测验证（2026-08-27，容器内 autogen-agentchat 0.7.5）**：
- ✅ `GraphFlow` + `DiGraphBuilder` 能构建多节点 fan-out 图（keling → xiaoyan, keling → xiaoma）
- ✅ `DiGraphBuilder` 源码确认 `activation_group`（并行组）+ `activation_condition="all"|"any"`（汇聚条件）
- ✅ 官方 docstring 示例就有并行组：`add_edge(agent_c1, agent_b, activation_group="loop_back_group", activation_condition="any")`
- ✅ `GraphFlow.run_stream` 支持流式输出（前端协议兼容）

**结论：框架原生就有并行能力（GraphFlow + DiGraphBuilder 的 activation_group），我们没用它，反而自己写 asyncio.gather 兜底。**

### 2.2 兜底性开发的完整清单

#### A 类：掩盖框架能力的兜底（异端，必须铲除）

| # | 位置 | 兜底内容 | 框架本有能力 |
|---|------|---------|-------------|
| 1 | `group_engine.py` `TeamEngineUnavailable` | 框架引擎不可用时抛异常 → `GroupChatManager.stream_send` 回退 legacy parallel fallback（asyncio.gather） | **GraphFlow 并行 fan-out** |
| 2 | `agent_manager.py` `HAS_REAL_AGENT = False` | AG2 导入失败时降级 | 应直接报错，不降级 |
| 3 | `group_engine.py` `TEAM_AVAILABLE = False` | autogen_agentchat 导入失败时降级 | 应直接报错，不降级 |
| 4 | `agent_manager.py` `mock_mode` | 无模型时 mock 回复 | 学习项目应配好模型走真实模式，mock 是逃避 |
| 5 | `main.py` mock_mode 自动检测 | 无默认模型配置 → mock 兜底 | 应明确报错提示配置模型 |

#### B 类：合理的工程容错（不是异端，保留）

| # | 位置 | 兜底内容 | 说明 |
|---|------|---------|------|
| 1 | `useChatSocket.ts` | `crypto.randomUUID` 在 http 域名不可用 → `getRandomValues` | 真实环境兼容，合理 |
| 2 | `cloud_space` | `errors="replace"` 处理乱码 | 真实文件解析容错，合理 |
| 3 | `nginx.conf` | SPA fallback | 前端路由标准做法，合理 |
| 4 | `useChatSocket.ts` | 断线 3 秒自动重连 | 网络容错，合理 |

**关键区分**：A 类是「没学框架能力，自己实现劣化兜底」——异端；B 类是「真实工程容错」——合理。用户愤怒的是 A 类。

### 2.3 为什么会出现 A 类兜底

1. **开发时没查框架能力**：MAS 改造（Phase 2）选 SelectorGroupChat 时，没意识到 GraphFlow 的存在（0.7.x 实验性新特性），所以群聊只有「串行讨论」一种模式。
2. **「兜底」成了习惯**：每次遇到「框架能力不满足」，第一反应是「自己实现降级兜底」，而不是「查框架有没有原生能力」。
3. **汇报时只说 OK**：每次做到一半问「有没有偏移方向」，汇报都是「完全 OK」，没有主动暴露「这里用了兜底，框架其实有原生能力」。

## 三、改进方案：用框架能力替换兜底

### 3.1 核心原则

> **学习项目，学的是框架能力。任何「自己实现降级兜底」都是异端。遇到框架能力不满足，先查框架有没有原生能力；有就用框架的，没有才考虑自研（且要明确标注为「框架无此能力，自研扩展」）。**

### 3.2 群聊模式化（用 GraphFlow 实现并行）

```
群聊模式（GroupChatMode）
├── discussion（讨论）   → SelectorGroupChat（串行共享对话流，保留）
├── supervisor（主管）   → SelectorGroupChat + supervisor selector（保留）
├── parallel（并行独立） → GraphFlow + DiGraphBuilder（新增一等模式，替代 legacy fallback）
└── hybrid（混合）       → 先并行独立评估 → 再串行讨论（进阶）
```

**Parallel 模式设计（用框架原生 GraphFlow）**：
```python
from autogen_agentchat.teams import DiGraphBuilder, GraphFlow

builder = DiGraphBuilder()
# 入口：用户消息
builder.add_node(entry_agent)          # 任务分发节点
# 并行 fan-out：三个成员独立响应（activation_group 并行）
builder.add_node(keling, activation='all')
builder.add_node(xiaoyan, activation='all')
builder.add_node(xiaoma, activation='all')
builder.add_edge(entry_agent, keling, activation_group='fanout')
builder.add_edge(entry_agent, xiaoyan, activation_group='fanout')
builder.add_edge(entry_agent, xiaoma, activation_group='fanout')
# 可选 join：汇总节点
builder.add_node(summarizer)
builder.add_edge(keling, summarizer)
builder.add_edge(xiaoyan, summarizer)
builder.add_edge(xiaoma, summarizer)
graph = builder.build()
team = GraphFlow(participants=[...], graph=graph, ...)
```

**关键点**：
1. **独立上下文**：GraphFlow 每个节点是独立 Agent 实例，各自独立上下文（不共享对话流）——这才是「三个独立的人」
2. **并行执行**：`activation_group` 让三个成员并行跑（墙钟时间 = 最慢者，不累积）
3. **流式输出**：GraphFlow 的 `run_stream` 同样产出 `ModelClientStreamingChunkEvent`，前端协议零变更
4. **失败隔离**：GraphFlow 节点级失败不影响其他节点（框架原生）

### 3.3 铲除 A 类兜底

| # | 兜底 | 铲除动作 |
|---|------|---------|
| 1 | `TeamEngineUnavailable → legacy parallel fallback` | 用 GraphFlow 实现 parallel 模式，删除 legacy fallback |
| 2 | `HAS_REAL_AGENT = False` 降级 | 改为直接报错（AG2 是核心依赖，缺失就是环境错误） |
| 3 | `TEAM_AVAILABLE = False` 降级 | 改为直接报错 |
| 4 | `mock_mode` | 学习项目默认走真实模式；无模型时明确报错提示配置，不 mock |
| 5 | `main.py` mock 自动检测 | 改为明确报错提示配置模型 |

## 五、风险与兼容性

| 风险 | 应对 |
|------|------|
| GraphFlow 是实验性 API（0.7.5 标注 experimental） | 锁定版本；API 变更时跟进迁移 |
| 并行执行 token 成本上升（各自独立上下文） | 并行成员用深模型，汇总用快模型；控制成员数 |
| 前端协议兼容 | GraphFlow 的 run_stream 产出 chunk 事件，前端零变更 |
| 群聊延迟（串行→并行） | 并行墙钟时间 = 最慢者，不累积，显著改善 |

1. **任何「降级/兜底/fallback」代码，必须先在框架文档/源码里查证框架是否有原生能力**；有就用框架的，没有才自研，且要在代码注释里写明「框架无此能力，自研扩展」。
2. **汇报必须主动暴露兜底**：每次汇报「完全 OK」前，自查一遍「这里有没有用兜底掩盖框架能力」。
3. **学习项目默认走真实模式**：mock 只用于 CI 测试，不用于日常开发。
4. **代码评审时，出现「兜底/降级/fallback」字样要重点审查**：是合理的工程容错，还是掩盖框架能力的异端？
