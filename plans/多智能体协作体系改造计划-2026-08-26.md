# 多智能体协作体系改造计划

> 日期：2026-08-26
> 状态：待评审
> 背景：使用中发现"员工彼此不知道对方"（可灵不知道小研是谁）。经业界调研确认，这不是单点 Bug，而是多智能体系统五层标准架构的系统性缺失。本计划按业界标准体系完整改造，不做补丁式修复。

---

## 一、问题定义与根因

**现象**：问可灵"小研在做什么？"，可灵回答"没有找到相关信息"。

**根因**（三层隔离）：

| 层面 | 代码位置 | 问题 |
|------|---------|------|
| 人设层 | `agent_manager.py` `_build_agent_instance()` | system_message 只含自己的人设，无团队信息 |
| 记忆层 | `vector_memory.py` `search()` | 按 agent_id 硬过滤，记忆完全私有 |
| 群聊层 | `agent_manager.py` `GroupChatManager.stream_send()` | 被 @ 的成员各自独立回复同一条消息，彼此看不到对方输出 |

**定性**：项目当前是"多个单 Agent 并排"（业界称 multi-washing），当初选 AG2 的核心理由——GroupChat 编排能力——尚未真正使用。

---

## 二、技术底座决策（一次说清，不再纠结）

### 决策：统一使用 autogen-agentchat 新 API 的团队原语

**背景知识**：AG2 生态有两套 API：

| | 经典 API（`ag2` 包） | 新 API（`autogen-agentchat` 包） |
|---|---|---|
| 群聊原语 | `GroupChat` + `GroupChatManager` | `SelectorGroupChat` / `RoundRobinGroupChat` / `Swarm` / `MagenticOneGroupChat` |
| 风格 | 回调式、全局 config | 事件驱动、异步流式、类型化消息 |
| 状态 | 维护模式 | **官方主推方向** |

**决策依据**：
1. 项目代码已经在用新 API（`from autogen_agentchat.agents import AssistantAgent`，实测版本 0.7.5）
2. 新 API 是事件驱动 + 原生 async 流式，与本项目 WS 流式协议天然契合；经典 API 反而要写适配层
3. 业界最佳实践：新项目一律用 autogen-agentchat 0.4+ 的事件驱动 API

**结论**：群聊引擎用 **`SelectorGroupChat`**（LLM 根据各成员的角色描述自动选下一个发言者）；@路由 用其原生 `selector_func` 扩展点实现；后续 Handoff 用 **`Swarm`**。经典 `ag2.GroupChatManager` 不引入。

## 三、目标架构总览

```
┌─────────────────────────────────────────────────────────┐
│ L4 A2A 协议层   /.well-known/agent-card.json + 任务接口    │ ← Phase 5
├─────────────────────────────────────────────────────────┤
│ L3 组织编排层   Supervisor 模式(可灵) + delegate 委派工具   │ ← Phase 3
├─────────────────────────────────────────────────────────┤
│ L2 会话协调层   SelectorGroupChat 替换自研平行响应          │ ← Phase 2
├─────────────────────────────────────────────────────────┤
│ L1 静态认知层   TeamContext 团队花名册注入 system prompt    │ ← Phase 1
├─────────────────────────────────────────────────────────┤
│ L5 共享状态层   记忆增加 scope 维度(私有/团队)              │ ← Phase 4
└─────────────────────────────────────────────────────────┘
```

依赖关系：L1 是地基 → L2 依赖 L1（选人靠角色描述）→ L3 依赖 L2 → L4/L5 相对独立。

## 四、分期改造清单

### Phase 1：L1 团队认知层 —— 花名册注入

> 对应业界做法：所有框架标配。Agent 的"同事认知"是显式注入的结构化上下文，不是模型涌现。

**改造前**
- 每个 Agent 的 system_message = 自己的人设 + 工具使用准则
- 可灵不知道小研/小码的存在，无法转述、无法推荐、无法协作

**改造后**
- 每个 Agent 的 system_message 自动附加「团队通讯录」章节：全部在职成员的名字、角色、职责一句话、专长工具
- 排除自己（不自我介绍成第三者）
- 成员入职/离职/改名/改角色时，全员实例自动重建（花名册保持新鲜）

**改动点**

| 文件 | 改动 |
|------|------|
| `backend/app/agents/team_context.py`（新建） | `build_roster(exclude_agent_id)` 从 AgentManager 元数据生成花名册文本；缓存 + 失效机制 |
| `backend/app/agents/agent_manager.py` | `_build_agent_instance()` 注入花名册；`create_agent/delete_agent/update_agent/rebuild_agent` 后触发全员重建 |

**验收标准**
- 问可灵"你们团队有谁？小研是做什么的？"→ 能准确回答角色职责
- 问可灵"这个问题该找谁？"→ 能推荐正确成员
- 招入新员工后，老员工立刻知道 TA（无需重启）

**价值差异点**：一行 prompt 级别的改动，但补上的是"组织认知"的地基。面试叙事：「Agent 的相互认知不是涌现的，是我工程化构造的上下文，并且维护了失效一致性」。

---

### Phase 2：L2 会话协调层 —— 真·群聊引擎

> 对应业界做法：AG2/AutoGen 的招牌能力 GroupChat + Speaker Selection。这是本项目选型 AG2 时最想要的叙事点。

**改造前**
- `GroupChatManager.stream_send()`：被 @ 的成员**并行独立**回复同一条消息
- 群里 @可灵 @小研 = 两个平行宇宙各自作答，互相看不到对方说了什么
- 无发言顺序协调、无讨论轮次概念

**改造后**
- 群聊房间按需构建 `SelectorGroupChat` 实例（participants = 房间成员，各带自己的 model client）
- **无 @**：LLM 选人机制根据成员角色描述决定谁先回应、是否需要第二人补充（如用户问技术问题 → 小码先答 → 可灵补充安排）
- **有 @**：通过 `selector_func` 强制被 @ 成员先发言，后续轮次交给 LLM 选人（其他人可自然接话）
- 终止条件：`MaxMessageTermination`（轮次上限）+ 所有被 @ 成员已响应即收敛
- 每个成员的发言仍是独立 message bubble、token 级流式（`model_client_stream=True` 时 chunk 事件穿透 `run_stream()` 输出）——**前端协议不变**
- mock 模式降级：无真实模型时保留旧并行路径，保证开发环境可用

**改动点**

| 文件 | 改动 |
|------|------|
| `backend/app/agents/group_engine.py`（新建） | 封装 SelectorGroupChat 构建/复用、selector_func(@路由)、终止条件、事件流 → (agent_id, chunk, message_id) 适配器 |
| `backend/app/agents/agent_manager.py` | `GroupChatManager.stream_send/send_message` 内部改为调用 group_engine；房间管理/持久化逻辑保留不动 |
| `backend/app/main.py` | WS group 分支基本不动（协议兼容）；仅透传新增的轮次边界事件（可选） |

**验收标准**
- 群里发"请小研和小码分别评估一下这个方案"，两人先后发言且**小码能看到并引用小研的观点**
- 群里发"这个 bug 怎么解决"（无 @），系统自动让小码主导、可灵收尾
- 前端渲染正常（每条发言独立气泡、流式打字效果不变）
- WS 测试脚本回归通过

**价值差异点**：从"自研平行响应"升级为框架原生 Speaker Selection——这正是选 AG2 的初心。面试叙事：「我用 SelectorGroupChat 实现了基于角色描述的自动发言调度，并用 selector_func 扩展点实现了产品级 @路由」。

---

### Phase 3：L3 组织编排层 —— 委派与主管

> 对应业界做法：Supervisor（主管路由）与 Handoff（平级移交）是 2025 年生产环境两大主流编排模式。

**改造前**
- 私聊中用户说"帮我问问小码"→ 可灵只能承认做不到
- Agent 之间没有任何通信通道

**改造后**
- **委派工具**：每个 Agent 注册 `delegate_to_colleague(target, question)` 工具（走 tool_registry），运行时可向指定同事发起子对话并取回结果，以自己的口吻转述给用户
- **主管模式**：群房间支持 `mode: "supervisor"`——由 owner（如可灵）接收消息、分析任务、@指派合适成员、汇总结论。与 Phase 2 的自由讨论模式并存，建群时可选
- 委派动作写入 tracing（delegate 事件类型），可在追踪页观察调用链

**改动点**

| 文件 | 改动 |
|------|------|
| `backend/app/tools/builtin.py` | 新增 `delegate_to_colleague` 工具实现（内部调 `agent_manager.send_message`，带深度限制防递归死循环） |
| `backend/app/agents/agent_manager.py` | `_build_agent_instance` 给所有 Agent 挂载委派工具；TOOL_USE_POLICY 补充委派准则（何时该找谁） |
| `backend/app/agents/group_engine.py` | supervisor 模式的 selector_func：固定 owner 先行、owner 通过特殊标记点名下一位 |
| `backend/app/models/__init__.py` + `group_engine.py` | GroupRoom 增加 mode 字段（默认 free/supervisor） |
| `frontend/src/components/workspace/*` | 建群弹窗加模式选择（自由讨论/主管调度） |

**验收标准**
- 私聊可灵："帮我问问小码 Python GIL 是什么"→ 可灵发起委派并以自己口吻转述答案
- supervisor 群："帮我做一份竞品分析"→ 可灵拆解任务 → 点名小研调研 → 收到结果后汇总输出
- tracing 页可见 delegate 调用链

**价值差异点**：补齐业界四大编排模式中的 Supervisor 与 Handoff（Pipeline 已有 Workflow 引擎覆盖）。面试叙事：「我实现了两种主流编排模式的对比：中心化 Supervisor 路由 vs 去中心化 Handoff 委派，并能讲清各自的成本与失控风险」。

### Phase 4：L5 共享状态层 —— 团队共享记忆

> 对应业界做法：MetaGPT 消息池 / LangGraph 共享 State / CrewAI crew 级 Knowledge。私有+共享分层是标准形态。

**改造前**
- 记忆检索 where 条件硬编码 `agent_id = 当前成员`
- 小研调研过的东西，可灵完全不知道

**改造后**
- 记忆元数据增加 `scope` 字段：`private`（默认）/ `team`
- 检索策略：先查私有记忆，不足时补充团队共享记忆（标注来源成员，如「来自小研的记忆」）
- 写入策略：成员回复中包含明确事实性内容时可选升格为 team scope（保守起见默认 private，Phase 4 先只做读侧共享 + 手动升格接口）
- 设置页提供开关：是否允许跨成员记忆检索

**改动点**

| 文件 | 改动 |
|------|------|
| `backend/app/memory/vector_memory.py` | `add()` 支持 scope 参数入库 metadata；`search()` 支持 `include_team` 合并查询（ChromaDB where `$or` 条件） |
| `backend/app/agents/agent_manager.py` | `retrieve_memories/build_memory_context` 传入 include_team 开关；enriched context 中标注记忆来源成员 |
| `backend/app/settings/router.py` 或 rag_config 同级 | 全局配置项 team_memory_enabled |
| `frontend/src/components/workspace/Settings*` | 开关 UI（若设置页已有结构则顺带） |

**验收标准**
- 先跟小研聊"我在研究 RAG 优化"，再问可灵"我们最近在研究什么"→ 可灵能引用小研的记忆（标注来源）
- 关闭开关后行为回退为纯私有

**价值差异点**：从"信息孤岛"到"团队共同知识"。面试叙事：「我设计了私有/团队两级记忆作用域，检索时合并并溯源标注」。

---

### Phase 5：L4 互操作协议层 —— A2A 协议暴露

> 对应业界做法：A2A（Google 发起，2025-06 捐赠 Linux Foundation，50+ 企业共建）是智能体互操作的事实标准。Agent Card 即"相互认知"的协议化表达。

**改造前**
- AiCumi 的员工只能在本平台内被访问，外部世界不可见

**改造后**
- 实现 A2A 最小服务面（原生 FastAPI 实现，不引重依赖）：
  - `GET /.well-known/agent-card.json`：全团队成员的能力名片（名字、角色、技能、工具列表）
  - 单成员粒度 Agent Card：`/api/a2a/{agent_id}/.well-known/agent-card.json`
  - `POST /api/a2a/{agent_id}/tasks/send`：符合 A2A Task 生命周期的最小任务接口（submitted → working → completed，返回 Message/Artifact 结构）
- 复用现有 `AgentManager.send_message` 作为执行后端；流式接口映射 SSE
- 效果：任何 A2A 客户端（或其他 AiCumi 实例）可以发现并委托本平台员工干活

**改动点**

| 文件 | 改动 |
|------|------|
| `backend/app/a2a/__init__.py`（新建包） | card 生成器 + task 状态机 + FastAPI 路由 |
| `backend/app/main.py` | 挂载 a2a router |
| `docs/` | 一篇 A2A 说明文档（含 curl 示例） |

**验收标准**
- `curl /.well-known/agent-card.json` 返回合法 Agent Card（名称/技能/能力声明）
- 用 A2A task 接口向小研发任务，能拿到 completed 状态 + 结果 artifact
- （加分验证）两个 AiCumi 实例互相把对方员工当外部专家委派

**价值差异点**：2025 年行业最大共识方向的落地，候选人中极少有人能讲。面试叙事：「我的平台不仅内部多智能体协作，还实现了 A2A 协议对外暴露，支持跨系统智能体发现与委托」。

## 五、改造前后总对照表

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 员工相互认知 | ❌ 完全孤立，互不知晓 | ✅ 全员持有实时团队通讯录 |
| "小研在做什么？" | ❌ "没有找到相关信息" | ✅ 准确回答角色/状态/近期工作 |
| 群聊 @多人 | ⚠️ 平行宇宙各自作答 | ✅ 有序发言、可见彼此观点、可接话补充 |
| 群聊无 @ | ⚠️ 仅房主响应 | ✅ LLM 按角色描述智能调度发言人与轮次 |
| 跨成员求助 | ❌ 不可能 | ✅ delegate 工具运行时委派 + 转述 |
| 组织模式 | Pipeline 一种（Workflow） | ✅ Pipeline + Supervisor + Handoff 三种 |
| 记忆模型 | 纯私有孤岛 | ✅ 私有 + 团队共享分层，来源可溯 |
| 对外开放 | ❌ 封闭系统 | ✅ A2A Agent Card + 任务接口，可被发现和委托 |
| AG2 使用深度 | 仅 AssistantAgent 单体 | ✅ SelectorGroupChat/Swarm/termination 全家桶 |
| 面试叙事 | "做了个多 Agent 平台"（易被追问穿） | "按业界五层体系实现完整 MAS 架构"（每层有实证） |

## 六、风险与兼容性

| 风险 | 应对 |
|------|------|
| SelectorGroupChat 多轮讨论 token 消耗上升 | 轮次上限终止条件；supervisor 模式本身比自由群聊更省 |
| 群聊延迟变长（串行发言 vs 原并行） | 产品语义本就应串行（对话需要上下文）；流式体验保证感知速度 |
| mock 模式下团队原语不可用 | 保留旧并行路径作为 mock 降级，CI 测试不受影响 |
| delegate 工具递归死循环 | 调用深度上限（建议 2 层）+ tracing 观测 |
| 共享记忆噪音污染 | 默认 private，team 升格需显式；沿用现有 `_is_memory_noise` 过滤 |
| 前端协议破坏 | Phase 1/2 设计为 WS 协议零变更；Phase 3 仅增量事件 |

## 七、明确不做的（边界）

- ❌ 不引入经典 `ag2.GroupChatManager` API（已决策统一新 API）
- ❌ 不做 MagenticOne/自主研究型团队（超出"同事团队"产品定位，可作为后续实验）
- ❌ 不做 FIPA ACL 级别的消息语义标准化（学术完备性无必要）
- ❌ 本期不改前端聊天交互范式（IM 式气泡保留）

## 八、执行约定（针对"决策分叉未约束"的复盘）

1. 本文档评审通过后即为架构约束，后续开发 Agent 的实现不得绕开五层体系自行发明协作机制
2. 每期完成后在本文档勾选并在 CHECKLIST.md 登记
3. 涉及框架原语选择的 PR，必须在描述中注明对应业界模式名称（Supervisor/Handoff/Blackboard…）
