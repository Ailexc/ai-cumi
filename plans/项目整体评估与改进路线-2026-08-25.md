> 项目周期：2026-08-16 立项 → 08-25，**9 天**
> 性质：客观评价，含问题清单与分级改进路线。所有结论均标注证据来源；未实测项明确标注。

## 一、项目定位回顾

> 「属于你个人的、云端的、全天候在线的 AI 助理团队」——自有聊天窗口（私聊/群聊）指挥一群有性格、有技能的 AI 员工，管理面"点一点"完成编排配置。

技术栈：AG2 (autogen-agentchat 0.7.5) + FastAPI/SQLite + React 19/Vite/Tailwind v4 + ChromaDB + Docker Compose 双容器。
规模：后端约 **9,200 行** Python、前端约 **9,000 行** TS/TSX、**105 个 REST/WS 端点**、14 篇自建文档。

---

## 二、总体评价

**一句话：以 9 天时间交付了一个功能版图完整、能真实跑通核心场景的多 Agent 助理系统，完成度远超同期个人项目水准；但工程纵深明显不均——"广度 90 分，深度 60 分"，且存在一个影响核心体验的架构缺口（详见三.1）。**

三个突出优点：

1. **版图完整且互相咬合**：从模型管理→Agent 编排→工具调用→记忆→RAG→审批→工作流→分布式→可观测性→文档中心，规划内模块（P0-P4）全部落地且相互打通（如模型配置同时供 Agent/RAG/记忆三方消费），CHECKLIST 59/59 完成；
2. **可观测与自解释意识强**：执行追踪（trace 事件链）、14 篇图文文档中心、详尽的 plans/ 复盘习惯——这在个人项目里极罕见，也是本次排查能快速定位问题的直接原因；
3. **真实可用而非 demo**：流式输出、群聊编排、HITL 审批、云空间预览都是真实现，今天的裸 JSON 修复后聊天链路质量已达到日常可用水平。

三个主要短板：

1. **短期对话历史缺失**（架构级，见下）；2. **测试覆盖极薄**（357 行测试 vs 18,000+ 行代码）；3. **部分能力是"演示级"而非"生产级"**（web_search mock、code_execute 无沙箱、限流仅展示）。

## 三、关键发现（按严重度排序）

### 🔴 发现 1：Agent 没有短期对话历史——多轮连贯性靠长期记忆硬撑

**证据**：`agent_manager.send_message()` 声明了 `conversation_history` 参数但函数体内从未使用；WS 主流程只传当前消息 `stream_message(room_id, enriched_content)`；群聊 `stream_send()` 同样无历史。

**后果**：每一轮对话对 Agent 来说都是全新会话。"我刚才说的第二点展开讲讲"、"把上面那段改成表格"这类**指代上文的能力天然缺失**，只能靠语义检索 top-5 长期记忆碰运气补救。这是目前**影响日常体验的最大架构缺口**。

**改进方向**：引入滑动窗口短期记忆——每次请求前从 messages 表加载最近 N 轮（如 10 轮），作为 AG2 消息列表传入（AG2 的 `on_messages_stream` 本就接受消息数组，改造量小）。长期记忆继续负责"跨会话事实"，短期窗口负责"本会话上下文"，两层各司其职。

### 🔴 发现 2：web_search 无 API Key 时返回 mock 假数据

**证据**：`builtin.py:47-62`，未配 `SERPER_API_KEY` 时返回构造的假搜索结果（含 `"note": "Configure SERPER_API_KEY..."`），而这段 note 会随结果一起进入模型上下文。

**后果**：模型可能基于**虚构的搜索结果**一本正经地回答用户——比报错危险得多。今天排查中已实际观察到模型回显过这种 mock JSON。

**改进方向**：无 Key 时直接返回明确的"搜索服务未配置"错误信息（让模型向用户如实说明），不虚构结果。

### 🟡 发现 3：测试覆盖与代码规模严重失衡

357 行测试（test_api 200 + test_ws 157）对应 18,000+ 行业务代码。今天修复的裸 JSON 问题若有集成测试兜底（问时间→断言非 JSON），不至于上线后才暴露。

**改进方向**：不必追求覆盖率数字，优先补三类测试：① 核心链路冒烟（发消息→断言自然语言回复；调工具→断言非 JSON）；② 今天修过的每个 bug 一个回归用例；③ 配置变更的端到端读回断言（本次 is_default 静默失败 bug 的直接教训）。

### 🟡 发现 4：安全姿态适合"纯内网个人使用"，不具备公网暴露条件

- 全部 105 个端点**无任何鉴权**（任何人可读写模型 Key、执行工具、删记忆）；
- `code_execute` 直接 `subprocess` 跑任意 Python，仅有超时保护，无沙箱隔离；
- 模型 API Key 有 Fernet 加密存储（✅ 这点做得好），但管理接口不设防等于加密意义减半。

**结论**：在 OrbStack 内网域名下运行是合理的个人定位，**但若未来暴露公网或接入外部 IM 渠道，鉴权是前置必修项**。建议至少加一层简单的 Bearer Token 中间件（半天工作量）。

### 🟡 发现 5：部分能力为"演示级"

| 能力 | 现状 | 差距 |
|---|---|---|
| web_search | 未配置时诚实报错（见发现 2） | 需真实搜索源 |
| 限流字段 | 仅元数据展示，请求路径不生效（文档中心已诚实标注） | 需计数器中间件 |
| 分布式 gRPC Runtime | 拓扑/健康检查/故障转移真实，但单机场景收益存疑 | 定位为学习/扩展储备即可 |
| OCR | 无（扫描件 PDF 提取文本为空） | 按需再上 |

### 🟢 做得好的（保持）

- **模型管理**：5 类模型统一管理、Fernet 加密、默认互斥、per-agent 绑定——设计成熟（今日发现的 is_default 字段 bug 属实现层笔误，已修）；
- **可观测性**：trace 事件链覆盖 agent_start/memory_query/model_call/tool_call，响应耗时 p50/p95 统计；
- **文档中心**：14 篇结构化图文文档 + 诚实的局限标注（如限流未生效的说明），自我解释能力极强；
- **记忆治理**（今日新增）：写入噪声过滤 + 存量清理 + 真实语义嵌入（1024 维），检索质量已实测达标。

## 五、改进路线建议

### P0 · 止血与核心体验（本周内值得做）

1. **短期对话历史窗口**（发现 1）——补齐后多轮对话体验质变，预计半天~一天工作量；
2. **web_search mock 移除**（发现 2）——改为诚实报错，半小时；
3. **RAG 全链路首测**——数据已就位，按《云空间 RAG 测试验证指南》跑一遍验收清单，暴露的问题当场修。

### P1 · 工程健壮性（下周）

4. 回归测试集：今日所有修复各沉淀一个用例 + 核心链路冒烟（发现 3）；
5. 简易 Bearer Token 鉴权中间件（为外部 IM 接入铺路）；
6. WS 断线自动重连（前端体验小痛点）；
7. trace 持久化到 SQLite（重启不丢观测数据）。

### P2 · 能力增强（按需触发）

8. RAG 关键词层（BM25+RRF）——触发信号见调研文档行动项④；
9. 记忆分层沉淀（对话流水自动提炼 fact/preference）；
10. 更多内置工具（日程/提醒类，契合"助理团队"定位）；
11. 外部 IM 渠道接入（飞书/Telegram，README 已列为可选能力）。

### P3 · 远期储备

12. code_execute 沙箱化（容器隔离/Deno 选项）；
13. SQLite → Postgres（多实例时才需要）；
14. 分布式 Runtime 的实际应用场景探索。
