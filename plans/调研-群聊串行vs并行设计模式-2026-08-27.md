# 调研：多智能体「群聊/团队协作」设计模式 —— 串行 vs 并行

> 日期：2026-08-27
> 背景：AiCumi 当前用 AG2 `SelectorGroupChat` 实现群聊（LLM 自动选发言人，串行共享对话流）。
> 用户质疑：三个真实的人应是独立个体、并行处理各自回应，而非串行轮询、共享思想。
> 本文基于业界真实框架事实（CrewAI / LangGraph / AutoGen-AG2 / MetaGPT / OpenAI Swarm / OpenAI Assistants），不联网。

---

## 0. 结论速览（TL;DR）

| 问题 | 结论 |
|---|---|
| 当前串行 SelectorGroupChat 是不是错的？ | **不是错，是"用错了场景"**。串行共享对话流是业界标准模式（GroupChat 类），适合"讨论/辩论/头脑风暴"；但用户描述的"三个专家各自独立评估"是 **Parallel/Independent** 模式，串行 GroupChat 确实不匹配。 |
| 业界"并行独立响应"的标准做法？ | **Fan-out / Fan-in**：同一任务并行分发给多个 Agent（各自独立上下文），各自产出，再汇总。CrewAI 的 `process=parallel`、LangGraph 的并行节点、AG2 的 `asyncio.gather` 都是这个模式。 |
| 真实群聊更像哪种？ | **两者都有**。真实群聊的"接收"是并行的（每个人同时看到消息），但"发言"受社会规范约束（一次一人说，别人等）。所以真实群聊 = **并行感知 + 串行发言** 的混合体。 |
| 并行是否天然更快？ | **是**（墙钟时间上），但总 token 成本不变甚至更高。并行真正的价值是**延迟不累积**，从而允许每个 Agent 用更慢更深的模型。 |
| AG2 0.7.x 有没有并行原语？ | **没有 GroupChat 级别的并行原语**。`SelectorGroupChat`/`RoundRobinGroupChat` 都是串行。并行靠 `asyncio.gather` + 独立 Agent 实例（业界标准做法）。 |

## 1. 业界多智能体协作的四种主流模式

### 1.1 Sequential / Pipeline（流水线）

- **定义**：任务按固定顺序经过多个 Agent，前一个的输出是后一个的输入。每个 Agent 只看到前序结果，不看到全局。
- **代表框架**：LangGraph（链式节点）、CrewAI（`process=sequential`）、MetaGPT（SOP 流水线：产品经理→架构师→工程师→QA）、AutoGen 早期 `ConversableAgent` 链。
- **适用场景**：有明确依赖关系的流水线（如"写需求→写代码→写测试→评审"）、SOP 化流程、数据转换管道。
- **特点**：结构清晰、可预测、易调试；但**延迟线性累积**，且中间 Agent 出错会阻断下游。

### 1.2 Parallel / Independent（并行独立）

- **定义**：同一输入/任务**同时**分发给多个 Agent，各自用**独立上下文**处理，互不干扰，最后汇总（Fan-out → Fan-in）。
- **代表框架**：CrewAI（`process=parallel`，多个 Agent 同时跑 task）、LangGraph（并行节点 fan-out/fan-in）、AG2（`asyncio.gather` 多个独立 Agent）、OpenAI Assistants（多个 thread 并行）。
- **适用场景**：多个专家各自独立评估/打分/调研/生成备选方案；需要多样性（diversity）的场景；子任务无相互依赖时。
- **特点**：墙钟延迟 = 最慢单个 Agent 的延迟（不累积）；上下文隔离（无串扰）；但**没有成员间讨论/引用**，无法互相修正。

### 1.3 Supervisor / Hierarchical（主管-分层）

- **定义**：一个 Supervisor（主管）Agent 负责拆解任务、分派给子 Agent、收集结果、汇总/决策。子 Agent 之间通常不直接通信，只与主管通信。
- **代表框架**：LangGraph（Supervisor 节点 + 子 Agent 节点）、AutoGen/AG2（`GroupChatManager` + 自定义 selector 实现主管路由）、CrewAI（Manager Agent）、MetaGPT（"老板"角色）。
- **适用场景**：任务需要拆解与汇总、需要有人对最终输出负责、子任务异构（不同领域专家）。
- **特点**：控制力强、可审计（主管是唯一决策点）；但主管可能成为瓶颈，且子 Agent 间缺乏横向协作。

### 1.4 Swarm / Handoff（群体-移交）

- **定义**：Agent 之间通过"移交（handoff）"把控制权转给另一个 Agent，每个 Agent 有专属上下文/工具，处理完自己的部分后决定交给谁。没有中央调度器，是**去中心化的接力**。
- **代表框架**：OpenAI Swarm（`handoff` 原语）、LangGraph（`Command`/`interrupt` 实现 handoff）、AG2 的 `HandoffMessage`（0.4+ 引入）。
- **适用场景**：客服路由（售前→售后→退款）、多步骤任务接力、每个 Agent 有明确职责边界且需要携带上下文转移。
- **特点**：灵活、可扩展；但流程不可预测，调试困难，容易"移交失控"（需要 max_iterations 兜底）。

### 1.5 四种模式对比表

| 维度 | Sequential | Parallel | Supervisor | Swarm/Handoff |
|---|---|---|---|---|
| 通信拓扑 | 链式 | 星型（汇聚） | 星型（主管中心） | 图（任意移交） |
| 上下文 | 前序结果 | 独立隔离 | 主管汇总 | 随移交携带 |
| 延迟 | 线性累积 | 不累积（=最慢者） | 主管串行瓶颈 | 取决于路径 |
| 成员间讨论 | 无 | 无 | 无（只与主管） | 无（只移交） |
| 控制力 | 高 | 低 | 最高 | 低 |
| 代表框架 | LangGraph/CrewAI/MetaGPT | CrewAI/LangGraph/AG2 | LangGraph/AG2/CrewAI | OpenAI Swarm/LangGraph |

> **关键洞察**：这四种模式里，**只有 GroupChat 类（AutoGen/AG2 的 GroupChat/SelectorGroupChat）是"成员共享对话流、互相可见、轮流发言"的第五种模式**——它本质上是"Sequential 的发言顺序 + 共享黑板（blackboard）"。业界通常把它归为 **Blackboard / Speaker-Selection** 模式，与上面四种正交。

## 2. 「并行独立响应」在业界是怎么实现的

### 2.1 CrewAI 的并行执行

- CrewAI 的 `Crew(process=Process.parallel)` 会让多个 Agent **同时**执行各自的 task（底层用 `asyncio.gather` / 线程池）。
- 每个 Agent 有**独立的上下文**（自己的 `memory`、自己的 task 输入），互不看到对方的中间过程。
- 汇总方式：CrewAI 本身不强制汇总，通常由后续的 Sequential 阶段或一个专门的"汇总 Agent"处理；或者每个 Agent 的 task 输出直接作为最终结果。
- **要点**：CrewAI 的并行是"任务级并行"（task 之间无依赖），不是"对话级并行"。

### 2.2 LangGraph 的并行节点（fan-out / fan-in）

- LangGraph 的 StateGraph 天然支持并行：一个节点有多条出边 → **fan-out**（多个节点同时跑）；多个节点汇聚到一个节点 → **fan-in**（汇总节点收到所有子节点的输出）。
- 每个并行节点操作的是**同一个 State** 的不同字段（`add` reducer 合并），但每个节点内部的 Agent 上下文是独立的。
- 这是 LangGraph 的核心卖点之一：**图拓扑天然表达并行**，且支持条件分支（conditional edges）。
- **要点**：LangGraph 的并行是"图节点级并行"，通过 State 的 reducer 做 fan-in 合并。

### 2.3 AutoGen / AG2 是否有并行群聊原语？

- **没有**。AG2（autogen-agentchat 0.7.x）的 `GroupChat`、`SelectorGroupChat`、`RoundRobinGroupChat`、`Swarm` 全部是**串行**的——同一时刻只有一个 Agent 在发言，消息按顺序追加到共享对话流。
- AG2 的并行能力来自**框架底层**而非群聊原语：
  - `asyncio.gather` 多个独立 `AssistantAgent` / `ChatCompletion` 调用；
  - `Team` 的 `run_stream` 本身是 async 的，可以多个 team 并行跑；
  - 但**没有**"一个 GroupChat 内部并行发言"的原语。
- 业界在 AG2 里实现"并行独立响应"的标准做法（见 §5.3）：
  1. 为每个成员创建**独立的 Agent 实例**（独立 model context）；
  2. 用 `asyncio.gather` 同时调用各自的 `run` / `run_stream`；
  3. 各自产出后，用一个汇总步骤（可以是 LLM 汇总，也可以是规则拼接）fan-in。

### 2.4 有没有「所有成员同时收到消息、各自独立回复、然后汇总」的标准模式？

- **有，这就是 Fan-out / Fan-in（Map-Reduce）模式**，是分布式系统和 MAS 的通用模式：
  - **Fan-out（Map）**：把同一输入广播给 N 个独立 worker；
  - **Fan-in（Reduce）**：收集 N 个结果，合并/汇总。
- 业界实现：
  - LangGraph：`Send` API（动态 fan-out）+ 汇总节点（fan-in）；
  - CrewAI：`process=parallel` + 后续汇总 task；
  - AG2：`asyncio.gather` + 汇总 Agent；
  - OpenAI Assistants：多个 thread 并行跑 + 汇总。
- **注意**：这个模式里"汇总"是关键设计点——是 LLM 汇总（一个汇总 Agent 读所有结果）、规则汇总（拼接/投票/加权），还是让用户自己看（不汇总，直接展示 N 个独立回复）。

## 3. 「共享对话流 vs 独立上下文」的权衡

### 3.1 串行讨论（共享对话流）适合什么场景？

- **头脑风暴**：成员需要看到彼此的 idea 并在此基础上发散（"接着 X 的想法，我觉得…"）。
- **辩论/评审**：成员需要反驳、补充、引用彼此观点（"我不同意 Y 的结论，因为…"）。
- **需要互相修正的场景**：一个 Agent 的推理可以被另一个 Agent 纠错。
- **需要收敛到共识的场景**：讨论最终要达成一致结论。
- **本质**：共享对话流 = **Blackboard 模式**，价值在于**信息共享与迭代**。代价是：上下文越长、token 成本越高、延迟线性累积、且"群体思维"（groupthink）风险——后发言者容易被前发言者带偏。

### 3.2 并行独立响应适合什么场景？

- **多个专家各自独立评估**：每个专家用自己的知识库/工具独立给出意见，不互相影响（避免锚定效应）。
- **各自调研/检索**：多个 Agent 同时查不同来源，互不干扰。
- **生成多样性候选**：多个 Agent 各自生成方案，供用户/汇总器挑选。
- **子任务无依赖**：任务可拆分为互不依赖的并行子任务。
- **本质**：并行独立 = **Map-Reduce 模式**，价值在于**多样性、隔离性、低延迟**。代价是：没有成员间讨论，无法互相引用/修正，需要额外的汇总层。

### 3.3 真实世界的「群聊」更接近哪种？

**关键洞察：真实群聊是"并行感知 + 串行发言"的混合体。**

- **感知层（并行）**：每个人**同时**看到消息（消息广播是并行的，没有"等别人看完"）。
- **发言层（串行）**：真实群聊里，同一时刻通常**只有一个人打字发言**（社会规范：一次一人说，别人等；即使有人同时打字，也是"抢话"而非"并行发言"）。
- **上下文层（混合）**：每个人有**独立的私人上下文**（自己的记忆、自己的草稿），但共享**公共对话流**（群聊记录）。
- **所以**：用户说"三个真实的人应该是独立个体、并行处理各自回应"——这在**感知和上下文**层面是对的（每个人独立看到、独立思考），但在**发言**层面，真实群聊依然是串行的（一次一人说）。

> **结论**：真实群聊 = **并行接收 + 独立上下文 + 串行发言**。当前 SelectorGroupChat 实现了"串行发言 + 共享对话流"，但**缺失了"独立上下文"**（所有成员共享一个对话流，后发言者能看到前面所有发言，这其实比真实群聊更"共享"）。而用户想要的"并行独立响应"则走向另一个极端（完全独立、无讨论）。

## 4. 性能与深度的权衡

### 4.1 并行是否天然比串行快？

- **墙钟时间（wall-clock）上：是**。串行 N 个 Agent 的总延迟 = Σ(每个 Agent 延迟)；并行 N 个 Agent 的总延迟 = max(每个 Agent 延迟)。N 越大，并行优势越明显。
- **但注意**：
  - **总 token 成本不变甚至更高**：并行不减少总计算量，只是把计算"摊平"到时间轴上。如果每个 Agent 都读完整共享上下文，并行反而可能更贵（各自维护独立上下文，重复读公共部分）。
  - **资源瓶颈**：并行受限于 API 并发配额（rate limit）、GPU/内存、网络带宽。N 个并行请求可能触发限流。
  - **汇总开销**：并行后通常需要汇总步骤，汇总本身是串行的，且汇总 Agent 要读 N 份结果（token 成本高）。

### 4.2 并行时每个 Agent 是否可以用更慢但更深的模型？

- **是，这正是并行的核心价值之一**。
  - 串行模式下，延迟累积，所以每个环节都倾向用快模型（否则总延迟爆炸）。
  - 并行模式下，延迟不累积（= 最慢者），所以**每个 Agent 都可以用更慢、更深、更强的模型**（如推理模型），因为它们的延迟被"摊平"了。
  - 业界实践：并行 fan-out 阶段用强模型（深度推理），fan-in 汇总阶段可以用快模型（只做归纳）或强模型（做综合判断）。
- **权衡**：并行 + 深模型 = 高质量 + 可接受延迟，但**成本线性增长**（N 个深模型调用）。适合"质量优先、预算充足"的场景。

## 5. AG2 / autogen-agentchat 0.7.x 的具体能力

### 5.1 SelectorGroupChat / RoundRobinGroupChat 是串行还是并行？

- **都是串行**。
  - `RoundRobinGroupChat`：按固定顺序轮流发言（round-robin），一次一人。
  - `SelectorGroupChat`：由 LLM（或 `selector_func`）每次选一个发言人，说完再选下一个，一次一人。
  - 两者都维护**一个共享的对话流**（`GroupChat` 的 message 列表），所有成员可见全部历史。
  - 当前 AiCumi 用的就是 `SelectorGroupChat`（`group_engine.py`），并加了 `selector_func` 实现 @路由和 supervisor 状态机——这些都是**串行调度**的扩展，不是并行。

### 5.2 有没有原生的并行执行 API？

- **没有 GroupChat 级别的并行原语**。AG2 的并行能力是"拼出来的"：
  - `asyncio.gather` 多个独立 Agent / Team 的 `run` / `run_stream`；
  - 多个 `AssistantAgent` 实例各自独立跑（每个实例有独立 model context）；
  - 但**没有** `ParallelGroupChat` 或类似原语。
- 事实上，AG2 官方文档明确把 GroupChat 定位为"串行对话"，并行需要开发者自己用 asyncio 组合。

### 5.3 业界通常怎么在 AG2 里实现「并行独立响应」？

标准做法（三步）：

1. **Fan-out**：为每个成员创建**独立的 Agent 实例**（关键：不能复用同一个实例，否则 model context 会串扰——AiCumi 的 `group_engine.py` 已经注意到这点："参与者实例每次运行时新建"）。每个实例只接收**任务消息**（不接收其他成员的发言），上下文完全独立。
2. **并行执行**：用 `asyncio.gather` 同时调用每个实例的 `run_stream`（或 `run`），各自产出流式结果。注意处理 `return_exceptions=True`（单个失败不拖垮整体）。
3. **Fan-in（汇总）**：收集所有结果后，选择汇总策略：
   - **LLM 汇总**：一个汇总 Agent 读所有结果，产出综合结论（适合需要统一结论的场景）；
   - **规则汇总**：拼接/投票/加权（适合结构化输出，如打分）；
   - **不汇总**：直接把 N 个独立回复展示给用户（适合"多个专家各自汇报"的场景——用户自己看）。

> **注意**：AiCumi 的 `agent_manager.py` 里已经有一个"legacy parallel fallback"路径（`asyncio.gather` + 每个 agent 独立 `send_message`），这正是 AG2 生态里"并行独立响应"的标准实现——只是它现在被降级为"框架不可用时的兜底"，而不是一等公民。

## 6. 当前设计的问题诊断

基于以上调研，当前 AiCumi 的串行 `SelectorGroupChat` 设计问题可以精确定位：

| # | 问题 | 严重度 | 说明 |
|---|---|---|---|
| 1 | **场景错配** | 高 | 用户期望的"三个专家各自独立评估"是 Parallel/Independent 模式，而 SelectorGroupChat 是 Blackboard/Speaker-Selection 模式。用讨论模式跑独立评估，成员会被彼此带偏（groupthink），且延迟线性累积。 |
| 2 | **共享上下文过度** | 中 | 真实群聊里每个人有独立私人上下文；当前所有成员共享完整对话流，后发言者能看到前面所有发言——比真实群聊更"共享"，丢失了独立性。 |
| 3 | **延迟线性累积** | 中 | 串行 N 个成员 = N 倍延迟。用户想用深模型时，串行会爆炸。 |
| 4 | **并行能力被降级** | 中 | 项目已有正确的并行实现（legacy fallback），但被定位为"兜底"而非"一等模式"，无法在 UI 上选择。 |
| 5 | **无汇总层** | 低 | 即使并行，也没有"汇总"设计点（LLM 汇总 / 规则汇总 / 不汇总），无法表达"各自汇报后综合"的意图。 |

**但要注意**：串行 SelectorGroupChat **不是错的**——它是业界标准的讨论模式。问题在于**当前系统只有一种模式**，无法表达"讨论"和"独立评估"两种不同的协作意图。

## 7. 架构层设计建议：把群聊改成「并行独立响应」

> 架构层面，不需要代码。核心思路：**把"群聊模式"从单一实现升级为"模式选择"**，并行独立响应作为一等模式。

### 7.1 核心设计：模式化群聊（Mode-based Group Chat）

把群聊从"一种实现"升级为"多种模式，用户/路由选择"：

```
群聊模式（GroupChatMode）
├── discussion（讨论）      → SelectorGroupChat（串行共享对话流）【现状】
├── supervisor（主管）      → SelectorGroupChat + supervisor selector【现状】
├── parallel（并行独立）    → Fan-out / Fan-in（asyncio.gather）【新增】
└── hybrid（混合）          → 先并行独立评估 → 再串行讨论【可选，进阶】
```

- **discussion / supervisor**：保留现有 `SelectorGroupChat` 实现（业界标准，适合讨论/主管场景）。
- **parallel**：新增一等实现，走 Fan-out / Fan-in（见 §7.2）。
- **hybrid**（进阶）：两阶段——先并行让每个成员独立评估（多样性），再把结果作为共享对话流输入，进入串行讨论（收敛共识）。这最接近真实世界的"先独立思考、再集体讨论"。

### 7.2 Parallel 模式的架构设计

```
用户消息
   │
   ▼
┌─────────────────────────────────────────────┐
│ Fan-out（Map）                              │
│   for each member:                          │
│     创建独立 Agent 实例（独立 model context） │
│     只注入：任务消息 + 该成员的私人记忆       │
│     不注入：其他成员的发言                    │
│   asyncio.gather(所有成员.run_stream)        │
└─────────────────────────────────────────────┘
   │  N 个独立流式结果（各自 message_id）
   ▼
┌─────────────────────────────────────────────┐
│ Fan-in（Reduce）                            │
│   策略 A：LLM 汇总（汇总 Agent 读全部结果）   │
│   策略 B：规则汇总（拼接/投票/加权）          │
│   策略 C：不汇总（N 个独立回复直接展示）      │
└─────────────────────────────────────────────┘
   │
   ▼
前端展示：N 个独立消息气泡（并行到达）+ 可选汇总气泡
```

**关键设计点**：

1. **独立上下文**：每个成员只看到"任务消息 + 自己的私人记忆"，**不看到其他成员的发言**。这是与串行模式最本质的区别。
2. **流式并行**：`asyncio.gather` 多个 `run_stream`，每个成员的 chunk 独立推送（前端已有 `chat.chunk` 协议，按 `message_id` 区分即可——AiCumi 前端协议零变更）。
3. **失败隔离**：`return_exceptions=True`，单个成员失败不影响其他成员（AiCumi legacy fallback 已这么做）。
4. **汇总策略可配置**：`parallel.summarize = none | rule | llm`，默认 `none`（各自汇报，用户自己看），可选 LLM 汇总。
5. **模型策略**：并行模式下每个成员可用更慢更深的模型（延迟不累积）；汇总 Agent 用快模型。
6. **终止/超时**：并行模式没有"发言轮次"概念，用 `asyncio.wait` + 超时（如 60s）控制，超时成员标记"未响应"。

### 7.3 与现有系统的衔接

- **复用 legacy parallel fallback**：`agent_manager.py` 里已有的 `asyncio.gather` 并行路径就是 Fan-out 的正确实现，把它从"兜底"提升为"一等模式"，补上 Fan-in 汇总层即可。
- **模式选择入口**：建群弹窗已有"模式选择卡片"（free/supervisor），加一个 `parallel` 选项。
- **记忆 scope**：并行模式下成员用 `private` 记忆（各自独立），不用 `team` 记忆（避免串扰）。
- **tracing**：并行模式记录 fan-out/fan-in 事件，方便学习调试（符合 AiCumi"透明优先"原则）。
- **降级**：`parallel` 模式在无模型环境同样走 mock 并行（每个成员 mock 回复）。

### 7.4 何时用哪种模式（决策指南）

| 用户意图 | 推荐模式 | 理由 |
|---|---|---|
| "你们讨论一下这个问题" | discussion | 需要互相引用、迭代、收敛 |
| "你们各自评估一下这个方案" | parallel (none) | 需要独立意见、多样性、避免锚定 |
| "你们各自调研，然后综合结论" | parallel (llm) | 独立调研 + 汇总 |
| "你先拆解任务，分派给大家" | supervisor | 需要主管拆解与汇总 |
| "先各自想，再一起讨论" | hybrid | 最接近真实世界的协作 |

## 8. 参考：业界框架事实清单

- **AutoGen / AG2（autogen-agentchat 0.7.x）**：`GroupChat` / `SelectorGroupChat` / `RoundRobinGroupChat` / `Swarm` 全部串行；无并行群聊原语；并行靠 `asyncio.gather` + 独立实例。`HandoffMessage`（0.4+）支持 Swarm 模式。
- **CrewAI**：`process=sequential | parallel | hierarchical`；并行 = 多个 Agent 同时跑 task（asyncio 底层）；hierarchical = Manager Agent。
- **LangGraph**：StateGraph 天然支持并行（fan-out/fan-in）、条件分支、`Send` API（动态 fan-out）、Supervisor 模式、`Command`/`interrupt`（handoff）。
- **MetaGPT**：SOP 流水线（Sequential），角色分工明确（产品经理→架构师→工程师→QA）。
- **OpenAI Swarm**：`handoff` 原语，去中心化接力（Swarm/Handoff 模式）。
- **OpenAI Assistants**：多 thread 并行（Parallel/Independent 模式）。
- **通用模式**：Fan-out/Fan-in（Map-Reduce）、Blackboard（共享对话流）、Supervisor、Handoff。

## 9. 一句话总结

> **当前串行 SelectorGroupChat 不是错的，是"只有一种模式"不够。** 业界标准做法是：讨论用串行共享对话流（Blackboard），独立评估用并行 Fan-out/Fan-in（Map-Reduce）。真实群聊是"并行感知 + 独立上下文 + 串行发言"的混合体。建议把群聊升级为**模式化**（discussion / supervisor / parallel / hybrid），并行独立响应作为一等模式，复用现有 legacy parallel 实现 + 补 Fan-in 汇总层。
