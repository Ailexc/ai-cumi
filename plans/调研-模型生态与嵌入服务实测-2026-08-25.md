## 一、AG2 模型客户端生态（联网核实）

### 1.1 官方客户端矩阵（autogen-agentchat 0.7.5）

| 客户端 | 协议 | 状态 |
|---|---|---|
| `OpenAIChatCompletionClient` | OpenAI 原生 + **任意 OpenAI 兼容端点**（base_url） | 稳定 |
| `AzureOpenAIChatCompletionClient` / Azure AI Foundry | Azure | 稳定 |

|---|---|---|
| 阿里百炼 DashScope | `https://dashscope.aliyuncs.com/compatible-mode/v1` 或业务空间专属域名 `/compatible-mode/v1` | chat + **embeddings** + function calling 全支持；可直供 DeepSeek/Kimi/GLM/MiniMax |

## 二、DashScope「域名 × 协议」矩阵（base_url 之谜的正解）

### 2.1 两个独立维度

| 维度 | 取值 | 说明 |
|---|---|---|
| **域名** | `https://dashscope.aliyuncs.com` | 统一老域名（官方文档默认给出） |
| | `https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com` | **业务空间专属域名**（新）。官方推荐迁移：性能与稳定性更好；老域名仍可用 |
| **协议路径** | `/api/v1/...` | DashScope **原生协议**（自有请求格式，如 `{"input":{"texts":[...]}}`） |
| | `/compatible-mode/v1/...` | **OpenAI 兼容模式**（标准 OpenAI SDK 格式；chat 与 embeddings 均支持） |

### 2.2 有效组合矩阵（实测）

| 组合 | 有效性 | 说明 |
|---|---|---|
| 老域名 + `/api/v1`（原生） | ✅ | AiCumi RAG 模块的 `DashScopeEmbeddingProvider` 走这条 |
| 老域名 + `/compatible-mode/v1` | ✅ | 实测 chat/embeddings 均通 |
| 业务空间域名 + `/compatible-mode/v1` | ✅ | 控制台推荐；chat 已在用；**embeddings 官方文档同样推荐此域名** |
| 业务空间域名 + `/api/v1`（原生路径） | ❌ | 用户实测报错。业务空间域名面向 compatible-mode；且 API Key 与地域/域名绑定，跨用会 401 |

> **原则：域名和协议路径必须配套，禁止交叉混搭。**

### 2.3 AiCumi 内部的隐藏坑（开发必读）

同一个 embedding 配置有**两个消费方，需要的协议不同**：

1. **RAG/知识库模块**（`knowledge/indexer.py::_get_embedding_provider`）：检测到 dashscope 即走原生 `DashScopeEmbeddingProvider`，其 URL 拼接逻辑要求 base_url 以 `/api/v1` 结尾——若把配置改成 compatible-mode，它会拼出 `.../compatible-mode/v1/api/v1/services/...` 这种错误 URL 而**挂掉**；
2. **记忆系统**（`memory/vector_memory.py`）：标准 OpenAI client，需要 `/compatible-mode/v1`。

→ **直接改配置会让"一边修好另一边坏"**。正确做法见第五节行动项②。

## 三、MiMo vs Qwen 工具调用对比实测

测试方法：容器内构造 AssistantAgent（绑定 `datetime_utils`），分别用 MiMo-v2.5（id=1）与 qwen3.7-flash（id=3）跑真实推理，观察工具调用参数与最终回答。

### 3.1 测试结果

**场景 A：完整 schema（修复后，含 enum）×「现在几点了？」**

| 模型 | 工具调用 | 回答 |
|---|---|---|
| MiMo | ✅ `{"action": "now"}` | ✅ 自然语言报时 |
| Qwen | ✅ `{"action": "now"}` | ✅ 自然语言报时 |

**场景 B：劣化 schema（无 enum、描述仅参数名，模拟修复前 bug）× 各 2 轮**

| 轮次 | MiMo | Qwen |
|---|---|---|
| 第 1 轮 | ✅ 猜对 `now` | ❌ 瞎猜 `get_current_time` |
| 第 2 轮 | ❌ 瞎猜 `get_current`，且把 `<tool_call>` XML 标签当文本吐出 | ❌ 瞎猜 `get_time` |

**场景 C：「哈喽」寒暄 × 完整 schema（未注入 TOOL_USE_POLICY）**

| 模型 | 行为 |
|---|---|
| MiMo | ⚠️ 寒暄也调了时间工具，回答硬塞报时 |
| Qwen | ✅ 正常问候，不调工具 |

### 3.2 分析与修正

1. **修正此前说法**："MiMo function calling 能力弱"不准确——原始事故主犯是我们的 schema 劣化 bug。完整 schema 下 MiMo 表现正常。
2. **同时修正**："Qwen 没 enum 也能读描述正确传参"也被实测推翻——**劣化 schema 下两个模型都不可靠，只是翻车姿势不同**。
3. **Qwen 确实更稳**：判断力更好（寒暄不调工具）、失败模式更体面（不吐 XML 标签）。
4. **核心工程教训（最重要）**：
   > **schema 质量 > 模型选择。** enum、参数描述必须完整写入函数签名注解；永远不要指望模型的聪明程度来兜底糟糕的工具定义。我们已落地的修复（`Literal`/`Annotated` 签名 + `TOOL_USE_POLICY`）正是针对这两点的防御，实测证明有效（MiMo 在策略注入后寒暄行为也恢复正常）。

## 四、qwen3.7-text-embedding 文档要点与实测

### 4.1 官方规格（help.aliyun.com/zh/model-studio/embedding）

| 项目 | 规格 |
|---|---|
| 支持维度 | **2560 / 2048 / 1536 / 1024（默认）/ 768 / 512 / 256**，`dimensions` 参数切换 |
| 批次大小 | 单次最多 **20 条**文本；单批最大 128K token |
| 价格 | 0.0005 元/千 token；新用户 100 万 token 免费额度（90 天） |
| 语种 | 201 种 |
| 高级功能 | `text_type`（query/document 区分）、`instruct` 任务指令、稀疏向量（dense&sparse）——**仅 DashScope 原生 API 支持，OpenAI 兼容模式不支持** |
| 官方定位 | 当前性能最强的文本向量模型；指令遵循比 text-embedding-v4 提升 16.4% |

### 4.2 实测验证

**① dimensions 参数可用**（经 OpenAI 兼容模式）：

```
dimensions=256  → 返回 256 维 ✅
dimensions=512  → 返回 512 维 ✅
dimensions=1024 → 返回 1024 维 ✅
```

**② 语义检索质量：真嵌入 vs 现状 hash 嵌入（决定性数据）**

```
查询："用户喜欢什么咖啡"

真实嵌入余弦相似度：
  0.5875 ← 我喜欢喝美式咖啡，不加糖的    ← 正确命中，区分度 3 倍+
  0.1800 ← 明天下午三点开会
  0.1941 ← 北京今天下雨了

本地 hash 嵌入（现状）：
  0.0000 ← 我喜欢喝美式咖啡，不加糖的    ← 完全失效！
  0.0000 ← 明天下午三点开会
  0.0000 ← 北京今天下雨了
```

> **结论**：hash 嵌入本质是关键词匹配，查询换个说法就全灭（相似度全 0）。这就是为什么记忆系统经常检索不到/检索错。启用真实嵌入是记忆系统可用的前提，不是锦上添花。

### 4.3 高级特性在 OpenAI 兼容模式下的支持度（判定实验）

> 背景：官方文档称 text_type/instruct/稀疏向量"仅支持通过 DashScope SDK 及 API 启用"。为验证真伪做了判定实验——HTTP 200 不代表参数生效（可能被静默忽略），因此采用**向量对比法**：加参前后向量完全一致=被忽略；显著不同=真实生效。对照组（同文本重复调用）cos=0.999999，证明服务确定性。

| 特性 | 官方文档说法 | 实测真相 | 证据 |
|---|---|---|---|
| `dimensions` | 兼容模式支持 | ✅ 真实生效 | 精确返回 256/512/1024 维 |
| `instruct` | 称"仅 DashScope SDK 及 API" | ✅ **真实生效（文档已过时）** | 与基线 cos=0.959（远超对照噪声 0.999999）；记忆检索场景目标命中 0.5875→0.7072 |
| `text_type` | 仅原生支持 | ❌ 静默忽略 | 加参后向量与基线 cos=1.000000，完全一致 |
| 稀疏向量 `output_type=dense&sparse` | 仅原生支持 | ❌ 静默忽略 | HTTP 200 但响应无 sparse 字段 |

**结论**：
1. 兼容模式覆盖 4 项中的 2 项，且恰是最有用的 `instruct`（查询增强）与 `dimensions`（维度策略）；
2. 缺失的 `text_type`（非对称检索）与稀疏向量（混合检索）只影响 RAG 未来进阶，记忆系统与当前 RAG 基础检索不需要；
3. **"统一走 OpenAI 兼容模式"成为可行主线**；原生协议降级为"未来 RAG 混合检索的可选增强适配器"。
4. 方法论沉淀：判断"参数是否被支持"不能只看 HTTP 状态码，必须做向量差异判定实验。

## 五、行动项（开发指导，按序实施）

### ① LLM 默认切换到 qwen3.7-flash 【配置】
- `PUT /api/models/3` 设 `default_model=true`（同类互斥会自动取消 MiMo 的默认位）
- MiMo 保留作备选；其行为已被 TOOL_USE_POLICY 约束
- **验收**：重启后问时间/寒暄均正常，日志显示 default model 为 qwen3.7-flash

### ② embedding 统一走 OpenAI 兼容模式 【代码重构 + 配置】

**架构决策依据**（六维评估 + 4.3 实测）：OpenAI 兼容模式在标准化/可移植性/生态/维护成本/趋势五个维度全面胜出，且实测已覆盖 `instruct`+`dimensions`；原生协议仅剩 `text_type`+稀疏向量两个独占特性，降级为未来可选增强。

**实施内容**：
1. 新增统一 Provider 工厂（放在 `knowledge/embedding_provider.py`）：按 base_url 特征路由——含 `compatible-mode` → `OpenAIEmbeddingProvider`；DashScope 原生端点 → `DashScopeEmbeddingProvider`（保留，供未来混合检索用）；无 key → 本地 hash 兜底；
2. `knowledge/indexer.py::_get_embedding_provider` 改为调用该工厂（删除内联选择逻辑）；
3. `memory/vector_memory.py::_init_embedding/_get_embedding` 改为复用同一工厂（删除自带的 OpenAI 直连逻辑）——**消除嵌入调用双轨制**；
4. 配置侧：id=2 的 base_url 改为业务空间 compatible-mode 域名（与 chat 一致），设 `default_model=true`。

**验收**：`/api/memory/stats` 显示 `embedding_available: true`；RAG 索引/检索正常；两模块走同一工厂代码路径。

### ③ 重建记忆 collection 【运维操作】
- 旧数据为 256 维 hash 向量，与新 1024 维不兼容，ChromaDB 不允许混合维度
- 方式：清空 `data/memory` 下 collection（现有记忆均为测试对话，可弃；如需保留先导出文本再重嵌入）
- **验收**：重建后新增记忆为 1024 维；用"用户喜欢什么咖啡"这类换说法的查询能命中"我喜欢喝美式咖啡"

### ④ （可选进阶）检索增强：触发信号与路线选择 【远期迭代】

**场景定位**：本系统知识库以 **PDF / Word / Markdown** 为主（学习场景），Excel 暂不作为重点。基于此定位，兼容模式缺失的 `text_type` 与稀疏向量**均不阻塞当前需求**。

#### 4a. 两个缺失能力对本系统文档类型的适用性

| 文档类型 | 内容特征 | text_type | 稀疏向量 |
|---|---|---|---|
| Word/PDF 制度·指南·学习材料 | 自然语言长文 | ⭐⭐ 有增益，但 `instruct`（兼容模式可用）已部分覆盖同类能力 | ⭐ 低 |
| PDF 技术手册 | 参数/型号 + 教程混排 | ⭐⭐ | ⭐⭐⭐ 型号参数需精确匹配 |
| Markdown 笔记 | 散文为主，夹代码块/命令 | ⭐⭐ | ⭐⭐ 取决于是否常搜代码片段 |

#### 4b. 升级触发信号清单（出现任一再启动，避免过度设计）

| 触发信号 | 对应动作（按优先级） |
|---|---|
| 用户反馈"搜某型号/编号/错误码搜不到" | ① 先做 BM25+RRF 关键词层（见 4c，不动嵌入协议） |
| 长文档检索命中率偏低（短问句配长文） | ① 先调优 `instruct`（兼容模式可用）；② 仍不够再评估原生 `text_type` |
| 以上都做了仍不满足 | 最后才考虑 DashScope 原生混合检索 |

#### 4c. 混合检索的两条路线对比（关键架构事实）

> 即使将来需要关键词级精确匹配，**厂商稀疏向量不是唯一路径**：

| | 路线 A：DashScope 原生稀疏向量 | 路线 B：自建 BM25 + RRF 融合（推荐） |
|---|---|---|
| 原理 | 服务端生成 sparse 向量，稠密+稀疏联合打分 | 本地关键词索引（BM25/SQLite FTS5）与向量检索两路召回，倒数排名融合 |
| 供应商锁定 | 锁死 DashScope | 无，嵌入服务可任意更换 |
| 存储改造 | ChromaDB **不支持稀疏向量存储**，需额外建存储层 | FTS5/BM25 索引独立于向量库，加一张表即可 |
| 实施成本 | 高（协议+存储+检索三层都动） | 中（jieba 分词 + rank_bm25/FTS5 成熟方案，融合逻辑约 50 行） |
| 中文支持 | 好 | 好（jieba+BM25 成熟组合） |

```
用户查询 ─┬→ 稠密向量检索（现有 ChromaDB 路径）
          └→ 关键词检索（BM25 / SQLite FTS5）
                    ↓
              RRF 倒数排名融合 → 最终排序
```

**结论**：路线 B 更标准、更可控、可移植性强，是首选；DashScope 原生稀疏向量仅作为最后备选。`DashScopeEmbeddingProvider` 代码继续保留（经行动项②的工厂按需路由），但预期大概率用不到。

### ⑤ （可选）维度策略
- 记忆系统：1024 维（默认，性能/成本平衡点）
- 如未来记忆量大成本敏感：可降 512/256 维（`dimensions` 参数已实测可用）；注意**改维度必须再次全量重建 collection**
