为什么分布式

AiCumi 默认是单进程单体：AG2 编排器内嵌在 FastAPI 进程里，所有 Agent 共享一个进程的 CPU / 内存 / 模型客户端。单机模型在个人项目够用，但它有几道绕不开的天花板：

🧱 单机单体的三个天花板

  • 垂直扩展有限：加模型调用只能升级单机配置，成本线性涨
  • 资源互相挤占：一个 Agent 的长时间工具调用会拖慢所有对话
  • 故障域过大：进程一挂，全部 Agent 一起下线

📦 分布式带来的能力

  • 横向扩展：加 worker 机器就能扩容，Agent 分散部署
  • 隔离：不同 Agent 跑在不同 worker，互不拖累
  • 故障域缩小：单个 worker 挂了，其余 worker 继续服务，失败请求自动转移

分布式 Agent 系统要解决的三个核心问题（也是本篇的主线）：

  1. 拓扑与路由：Agent 注册到哪台机器？请求怎么找到它？（→ AG2 gRPC Worker Runtime 的 host/worker 拓扑）
  2. 负载均衡：同一 Agent 有多个副本时，请求均匀分给谁？（→ 轮询 + replica 机制）
  3. 故障恢复：worker 挂了之后，它的 Agent 怎么搬走、请求怎么不丢？（→ 健康检查 + failover）
本模块探索"目标形态"：在单机进程内自托管一套真实的 gRPC 分布式运行时（AG2 官方单机 demo 部署方式），拓扑、路由、故障转移全真，但节点仍是本机。
学习定位：这是 AiCumi 的 P2 探索模块——不追求"真的跑在多台机器上"，而是把分布式的协议与机制真实跑通：跨进程的 gRPC 消息、Agent 注册/路由、副本负载均衡、健康探测与自动故障转移。面试讲的是"机制"，不是"部署"。

AG2 gRPC Worker Runtime

AG2（AutoGen 继任者）自带一套分布式运行时，两个核心类（backend/app/distributed/manager.py 引入）：

🎛️ GrpcWorkerAgentRuntimeHost（协调者）

  • 管理类，监听 :50051（可用 DISTRIBUTED_PORT 环境变量覆盖）
  • 维护"路由类型 → 哪个 worker 持有"的注册表
  • 收到消息后路由到持有该 Agent 类型的 worker

🧵 GrpcWorkerAgentRuntime（工作节点）

  • 每个 worker 一个 runtime 实例，通过 gRPC 连到 host
  • 负责在本地注册 Agent（register_factory(route_type, factory)）
  • 接受 host 转发的消息，调用本地 Agent 处理

消息寻址用 AgentId(route_type, key)：route_type 是注册的路由类型（本项目 = agent_id，如 keling；副本是别名类型 keling__r1），key 是实例键（本项目固定 "default"）。host 端按照类型把消息路由到对应 worker，worker 端按类型从本地工厂实例化 Agent 处理。

拓扑：一个 host（协调者）+ N 个 worker（执行者）。Agent 按轮询规则分布到各 worker；被复制的 Agent 以 <id>__r1 别名类型挂到另一个 worker。

为什么是"进程内自托管"？

AG2 官方文档把这种 host + 多个 worker 跑在同一台机器的部署称为"单机分布式 demo"：gRPC 消息真实走 127.0.0.1 端口，注册/路由/反序列化全部是真实协议。对学习项目的好处：协议是真的、机制是真的，但零额外基础设施，一次 docker compose up 就能起。要真正跨机，只需把 worker 的地址从 127.0.0.1 换成远程 IP——代码结构不用变。

worker-executor 模式与设计取舍

Worker 上注册的 Agent 不是独立的 AG2 AssistantAgent，而是一个轻量代理 DistributedProxyAgent（manager.py 第 53-71 行）：

class DistributedProxyAgent(BaseAgent):
    """A worker-side agent that executes by delegating to the shared agent manager."""
    def __init__(self, name, agent_id, executor):
        self._agent_id = agent_id
        self._executor = executor      # async callable (agent_id, message) -> reply str

    async def on_message_impl(self, msg, ctx):
        content = getattr(msg, "content", "") or ""
        reply = await self._executor(self._agent_id, content)   # ← 委托
        return TextMessage(content=str(reply), source=self.id.key)

executor 由 main.py::_make_distributed_factory（第 45-65 行）注入——它把请求委托回进程内的 AgentManager：

async def executor(agent_id: str, message: str) -> str:
    return await am.send_message(agent_id, message)   # 复用真实 AG2 调用路径

def factory(route_type: str, worker_id: str):
    agent_id = route_type.split("__")[0]              # "keling__r1" → "keling"
    if agent_id not in am.agents:
        return None
    return DistributedProxyAgent(route_type, agent_id, executor)
请求路径：API → 管理器（选 worker）→ gRPC 到 worker → ProxyAgent 委托回进程内 AgentManager。虚线以下为"诚实取舍"标注。
这个设计取舍必须讲清楚（面试被问"你的分布式是真的吗"时，正确姿势是承认边界）：gRPC 拓扑、Agent 注册、消息路由、副本负载均衡、健康探测、故障转移都是真实协议与真实机制；但每个 worker 上的 Agent 是"代理"，真正产出回复的是进程内共享的 AgentManager。原因：① 个人项目只有一台机器，跨机部署无收益；② 复用进程内已打磨好的模型客户端、记忆、工具链路；③ 保留了"把 executor 换成远程 RPC"的平滑升级路径——机制不变，只换执行器。这正是 worker-executor 模式的精髓：分布式系统的一半是机制，一半是执行器，本项目把机制做真、执行器复用。

负载均衡与副本机制

负载均衡的目标：多个可用的执行单元（副本）之间均匀分发请求，避免单个 worker 过热。经典策略有三种：

策略原理适用场景本项目状态
轮询（Round Robin）维护计数器，请求依次分给每个副本，周而复始副本能力相同、请求耗时相近✅ 已实现
随机（Random）每次随机选一个副本简单、无状态；长尾略大🔜 扩展方向
最少连接（Least Connections）选当前在途请求最少的副本请求耗时差异大（Agent 调用最典型）🔜 扩展方向

本项目实现的是轮询 + 副本别名（manager.py _build_route_plan + send_message）：

  • 分布：Agent 按 idx % worker_count 轮询分配到 worker-1 / worker-2（_build_route_plan）。
  • 副本：配置了 replicate_agents 的 Agent（如 keling）会额外以 keling__r1 别名注册到另一个 worker 上，形成双副本。
  • 轮询分发：_agent_entries[agent_id] 记录该 Agent 的所有副本位置（worker + route）；_rr_index[agent_id] 是指针，entries[(idx + attempt) % n] 依次尝试——成功就推进指针（lb_round_robins 计数 +1）。
  • 失败自动跳过：某个副本失败（worker down / 异常）不会死磕，attempt 递增换下一个副本，全部失败才触发 failover。
keling 双副本轮询：奇数次请求打 worker-1，偶数次打 worker-2。副本让"一台 worker 挂掉"不至于让 Agent 完全不可用。
环境变量可调：DISTRIBUTED_WORKERS（默认 2）、DISTRIBUTED_PORT（默认 50051）、DISTRIBUTED_HEALTH_INTERVAL（默认 10s）。replicate_agents 目前是构造参数，复制名单可扩展成配置项。

健康检查与故障恢复

分布式系统必须假设"节点会挂"。本模块的健康与恢复机制分三层：

① 健康探测

每个 worker 注册一个专属探针 Agent（health__<worker_id>），管理器后台循环 _health_loop（默认每 10 秒）对每个 worker 执行 ping()：通过 gRPC 给探针 Agent 发一条 "ping" 消息，5 秒超时。ping 不通即判定 worker 失联。

② 故障转移（failover）

_failover_agent(agent_id) 把失联 worker 上的 Agent 重新注册到健康 worker：保留还活着的副本，把丢失的主路由用 _make_factory + register_factory 注册到某个健康 worker 上，然后更新 _agent_entries 并重置轮询指针。之后到达的请求自动走新位置。

③ 手工控制（故障模拟 API）

为了"可演示、可学习"，提供三个控制入口：mark_worker_down（模拟崩溃 + 立即 failover）、recover_worker（按路由计划重启 worker 并重新注册 Agent）、rebuild（全量重建 worker 池）。

故障恢复时序：健康循环发现 worker-1 失联 → failover 把 keling 迁到 worker-2 → 新请求自动转移；恢复接口把 worker-1 拉回并按路由计划重建。
方法触发方式行为
health_check()_health_loop 定时（10s）ping 所有 worker，失联者标 down 并对每个受影响 Agent 执行 failover
mark_worker_down(id)POST /api/distributed/workers/{id}/down停止 worker 模拟崩溃，立即 failover 其 Agent（无需等健康循环）
recover_worker(id)POST /api/distributed/workers/{id}/up重建 worker，按 _agent_entries 记录的归属重新注册 Agent
rebuild(agent_ids)POST /api/distributed/rebuild全量重算路由计划并重建 worker 池（只停 worker，host 保活复用）
演示玩法（也是学习验证）：先 POST /api/distributed/send 发几条消息看 stats.lb_round_robins 增长 → 把 worker-1 下线 → 再发消息，观察 stats.failovers +1 且回复正常返回 → 恢复 worker-1 → 拓扑复原。整个"崩溃-转移-恢复"闭环可反复演示。

踩坑:--loop asyncio

分布式模块上线时踩过一个很隐蔽的坑，值得单列一节：uvloop 与 grpc.aio 不兼容。

现象：服务启动后分布式运行时"看起来正常"（host 打印 ready），但一旦通过 gRPC 发消息就静默失败——HTTP/2 握手永远不完成，没有报错、没有超时，只有挂起。

根因：uvicorn 默认在 --loop uvloop 下运行，而 AG2 的 GrpcWorkerAgentRuntime 走的是 grpc.aio（gRPC 的 asyncio 实现）。grpc.aio 依赖 CPython 标准 asyncio 事件循环的内部行为，uvloop（C 扩展的事件循环替代品）与之不兼容，导致 HTTP/2 握手静默失败。修复就一行——强制用标准 asyncio 事件循环（backend/Dockerfile 第 31-33 行）：

# --loop asyncio is required: AG2's GrpcWorkerAgentRuntime uses grpc.aio which
# does NOT support uvloop (silently fails the HTTP/2 handshake).
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0",
     "--port", "8000", "--loop", "asyncio"]

同类坑（代码注释里也记录了）：

  • host 端口就绪竞态：GrpcWorkerAgentRuntimeHost.start() 返回时监听其实还没就绪，worker 立刻连接会失败。解法：_wait_for_host 用 asyncio.open_connection 轮询 TCP 端口直到可连。
  • worker 连接重试：worker 连接 host 失败时创建新的 runtime 实例重试（最多 15 次、间隔 0.5s），因为旧的 runtime 实例状态已不可信。
  • host 禁止重复类型：同一路由类型不能注册两次，所以探针 Agent 用 health__<worker_id> 按 worker 唯一命名；副本用 <id>__r1 别名类型避免与主副本冲突。
  • 工厂产出的类型必须匹配路由：AG2 校验工厂产出的 Agent 类型名与注册的 route_type 一致，因此 DistributedProxyAgent 实例必须以 route_type 命名（副本也同理）。
这类"静默失败"是最难排查的：没有报错、没有日志，只能靠"二分禁用"定位。排查思路记录：先怀疑协议层（换 --loop asyncio 验证），再怀疑启动顺序（端口轮询），最后怀疑类型约束（名字匹配）。面试讲这个坑 = 展示真实的分布式调试经验。

API 一览

分布式能力通过一组 REST 端点暴露（main.py 第 1353-1435 行），未启用时统一返回 503：

六个端点：两个只读（status/agents）+ 四个控制（send/rebuild/down/up）。_require_distributed() 统一做启用校验。
# 1) 查看拓扑
curl http://chat-server.aicumi.orb.local/api/distributed/status

# 2) 发送消息（走 gRPC + 轮询 + failover）
curl -X POST http://chat-server.aicumi.orb.local/api/distributed/send \
  -H "Content-Type: application/json" \
  -d '{"agent_id": "keling", "message": "用一句话介绍你自己"}'

# 3) 模拟 worker-1 崩溃 → 观察 failovers 计数 +1
curl -X POST http://chat-server.aicumi.orb.local/api/distributed/workers/worker-1/down

# 4) 恢复 worker-1
curl -X POST http://chat-server.aicumi.orb.local/api/distributed/workers/worker-1/up
运行前置条件：分布式管理器在 lifespan 启动阶段初始化（main.py 第 185-203 行），无 Agent 时优雅跳过（不阻塞服务）；DISTRIBUTED_* 环境变量可调端口、worker 数与健康间隔。

对比评分:AG2 生产部署 / Ray

业内参照：AG2 官方生产部署（多机 host + worker）、Ray（通用分布式计算框架，Ray Serve 托管 Agent）。评分原则：机制真实性 × 功能完整度 × 生产就绪度，1-5 星。

四维度自评：gRPC 协议、副本、健康、failover 都是真实机制；"跨机执行"是明确短板（单机自托管 + 进程内执行器）。
维度做了什么AG2 生产部署Ray Serve本项目
真实拓扑host + 多 worker 真实 gRPC 注册/路由，AgentId 寻址，副本别名类型5.0 ★5.0 ★4.5 ★
负载均衡轮询 + replica 双副本；随机 / 最少连接为扩展方向4.5 ★5.0 ★3.5 ★
故障恢复探针 ping + 定时健康循环 + 自动 failover + 手工 down/up/rebuild 控制4.0 ★5.0 ★4.0 ★
跨机执行单机自托管，executor 委托进程内 AgentManager（worker-executor 模式）5.0 ★5.0 ★2.5 ★
结论：分布式是本项目机制最真实的模块之一——gRPC 协议、Agent 注册、副本、健康探测、failover 全部真实跑通，且把"故障模拟"做成了可演示的 API。与生产级差距集中在两点：① 跨机执行（worker-executor 模式复用进程内执行器）；② 工程化（无自动发现、无配置中心、无监控告警）。面试叙事建议："我基于 AG2 的 gRPC Worker Runtime 实现了分布式 Agent 拓扑，支持 Agent 分布、副本负载均衡、健康检查与自动故障转移，并诚实标注了 worker-executor 模式的取舍。"
