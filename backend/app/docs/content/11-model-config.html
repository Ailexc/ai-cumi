统一配置中心定位

一个 Agent 平台要接的"模型"远不止聊天：对话 LLM、向量化 Embedding、视觉识别、联网搜索、代码执行……如果每个模块各存各的 Key、各配各的地址，管理就是灾难。模型配置中心的定位是：一个入口，管所有模型。

一句话定位

所有模型的 Key / 地址 / 能力 / 价格 / 限额 统一存一张表（model_configs），统一加密、统一脱敏、统一测试、统一绑定到 Agent —— 前端「模型」Tab 就是它的全部操作面。

核心职责（对应 REST API）

能力接口说明
列表 / 分组GET /api/models · GET /api/models/by-type按类型过滤；by-type 返回 models_by_type 分组结构（前端 Tab 用）
增删改POST /api/models · GET/PUT/DELETE /api/models/{id}新建/查询/更新/删除；更新时若带 api_key 会重新加密
测试连接POST /api/models/{id}/testLLM 发一条消息测延迟；Embedding 走 DashScope/OpenAI 双路径
消费方各模块通过 ModelManagementService 取解密 KeyRAG（_get_embedding_provider）、记忆系统、Agent 启动检测都在用

服务层核心是 backend/app/services/model_service.py 的 ModelManagementService（业务编排）+ ModelKeyEncryptor（密钥加解密），ORM 模型是 backend/app/models/__init__.py 的 ModelConfig，API 层在 backend/app/main.py。前端操作面是 frontend/src/components/workspace/ModelManagement.tsx。

通过 ModelType 枚举把模型分成 5 类，每类有且只有一个默认模型（default_model 布尔位，同类互斥）：

类型互斥默认的实现

add_model_config(is_default=True) 与 update_model_config(default_model=True) 都会先执行"同类清除"：把同 model_type 且 default_model == True 的其他行全部置 False，再设置新的默认 —— 保证任意时刻每类只有一个默认，消费方 get_default_config(model_type) 永远拿到唯一答案。

5 类模型卡片：LLM / Embedding / Vision / Search / Code，每类独立管理、各自持有默认模型与 Provider 列表。
设计意图：把"模型"当作可插拔资源而非写死的常量 —— 换个 Embedding 模型不用改代码，改配置 + 重新索引即可（详见 10 · 云空间与 RAG 的 Embedding 适配）。

能力参数

ModelConfig 为每个模型记录 7 个能力字段，描述"这个模型能干什么、能装多少"。这些字段落在 ORM 列上（backend/app/models/__init__.py），通过 ModelConfigCreate/Update 校验后写入：

参数含义典型值（参考）当前使用场景
embedding_dimensions向量输出维度千问 1024 · text-embedding-3-small 1536RAG 实验室显示"向量维度"提示
max_input_tokens单次输入上限32K / 128K / 200K配置展示（容量预估）
max_output_tokens单次输出上限4K / 8K / 64K配置展示
context_window总上下文窗口128K / 200K配置展示
supports_vision是否支持图片输入—配置展示（未来路由到 vision 能力）
supports_function_calling是否支持工具调用—配置展示（工具类 Agent 依赖它）
supports_streaming是否支持流式输出默认 True决定是否走 chat.chunk 流式协议

与 AG2 的衔接：model_info 兜底

AG2 的 OpenAIChatCompletionClient 需要知道模型能力（是否支持 function calling、token 上限）。对 OpenAI 官方模型它能自动识别；但自建端点 / 小众模型名会抛 ValueError。此时 build_model_client() 用 DEFAULT_MODEL_INFO 兜底：ModelInfo(vision=False, function_calling=True, json_output=True, structured_output=True, family=UNKNOWN, token_limit=4096) —— 保证任何兼容端点都能接进来（见 backend/app/agents/agent_manager.py）。

计费限量（诚实说明）

ModelConfig 还记录了价格与限流字段，这是对标 LiteLLM Proxy / One API 这类网关的"计费限量"维度：

字段含义默认值
price_per_1k_input_tokens每 1K 输入 token 价格（元）None
price_per_1k_output_tokens每 1K 输出 token 价格（元）None
rate_limit_rpm每分钟请求上限None
rate_limit_tpm每分钟 token 上限None
rate_limit_tpd每天 token 上限None
batch_size批量调用建议值32
必须诚实说明：目前这些字段只是"配置展示"（元数据），限流并没有在请求路径上强制执行。也就是说，填了 rate_limit_rpm: 10，模型仍然可以被无限次调用 —— 系统不会计数、不会拒绝、不会排队。这与 batch_size 不同：Embedding 分批（25 条/次）是真实生效的（见 DashScopeEmbeddingProvider.embed()），而 rpm/tpm/tpd 目前纯粹是"记在表里"。
面试叙事：诚实比吹牛加分。你可以主动说"限流字段已建模、前端可填，但执行层没做 —— 下一步计划用令牌桶（token bucket）中间件在 build_model_client 外面包一层，或直接接 LiteLLM Proxy 做路由与限流"。这正是"知道自己缺什么"的学习者姿态。

加密存储：Fernet + 主密钥

API Key 是最高敏感度数据，明文落 SQLite 是不可接受的。方案：Fernet 对称加密 + 主密钥持久化 + 哈希脱敏展示。

ModelKeyEncryptor（backend/app/services/model_service.py）

  • Fernet 对称加密：encrypt()/decrypt() 直接包装 cryptography.fernet.Fernet；入库存 api_key_encrypted（密文 Text 列）。
  • 主密钥派生：主密钥可以是任意字符串 —— master_key.encode()[:32].ljust(32, b"\x00") 截断/补齐到 32 字节，再 urlsafe_b64encode 成合法 Fernet Key。关键是"确定性派生"：同一主密钥每次算出同一个 Key，跨重启稳定可解。
  • 脱敏展示：hash_api_key_for_display() 返回 sk-****{sha256(key)[:8]} —— API 只回这个，前端永远看不到明文。

主密钥从哪来（backend/app/database.py）

# get_or_create_master_key()
if MASTER_KEY_FILE.exists():
    return MASTER_KEY_FILE.read_text().strip()
key = secrets.token_urlsafe(32)          # 首次运行自动生成
MASTER_KEY_FILE.write_text(key)          # 持久化到 data/.master_key
os.chmod(MASTER_KEY_FILE, 0o600)         # 仅属主可读写

启动顺序（main.py lifespan）：MODEL_MASTER_KEY 环境变量优先，否则读 data/.master_key 文件（没有就生成）→ 构造 ModelKeyEncryptor(master_key) 单例 → 所有加解密共用。data 目录在 docker-compose 里是 host 挂载卷，主密钥跟着数据卷走，重启不丢。

安全边界（诚实提示）：这是"防君子不防黑客"级别的保护 —— 主密钥就躺在同目录的 .master_key 文件里，拿到磁盘权限就拿到了全部 Key。生产级应该用 KMS / 环境变量注入 / 密钥轮换。但对学习项目，它正确示范了"密文落库 + 明文只出现在内存"这一核心原则。
加密存储双路径：写时加密落库、读时解密进内存，API 层永远只见哈希摘要。

测试连接：LLM / Embedding 双路径

"配完能不能用"是高频操作。前端每个模型行都有测试按钮，调用 POST /api/models/{id}/test → test_model()（backend/app/main.py），按类型分流：

LLM / 对话模型：chat.completions 实测延迟

# 构造 AsyncOpenAI 客户端（anthropic 默认补 base_url）
client = AsyncOpenAI(**client_kwargs)
resp = await client.chat.completions.create(
    model=model_name,
    messages=[{"role": "user", "content": "Say 'hello' in one word."}],
    max_tokens=10,
)
reply = resp.choices[0].message.content.strip()
latency = round((time.time() - start) * 1000)
return {"status": "ok", "reply": reply, "latency_ms": latency}

Embedding：双路径（DashScope 专用 URL vs OpenAI 格式）

test_model() 先做三路判定：provider == "dashscope" 或 "dashscope" in base_url 或 "qwen" in model_name → 走 _test_dashscope_embedding()；否则走 _test_openai_embedding()。两者都返回 连接成功，向量维度: N + 延迟。

千问 404 修复故事（真实的踩坑）

DashScope 的 Embedding 是专用服务端点（/api/v1/services/embeddings/text-embedding/text-embedding），不是 OpenAI 的 /v1/embeddings。最初实现直接拼 base_url + "/api/v1/services/..."，但只要用户在配置里把 base_url 填成已含 /api/v1 的完整地址（网上教程常见写法），请求就变成 /api/v1/api/v1/services/... → 404。修复：先判断 base.endswith("/api/v1")，是则不再重复拼 —— 测试连接与 RAG 的 Embedding provider（embedding_provider.py 同款逻辑）双双受益。
测试连接分流：LLM 走 chat.completions；Embedding 按 is_dashscope 判定走 OpenAI 格式或 DashScope 专用端点，统一回状态 + 延迟。

模型绑定与重启恢复

配置中心最终要回答一个产品问题：每个员工（Agent）用哪个模型？答案是三层：系统默认 → 全局默认模型 → per-agent 覆盖。

启动时自动检测默认模型（main.py lifespan）

# mock 自动检测：存在默认模型配置 → 真实模式，否则 mock 兜底
configs = service.get_all_configs()
default = next((c for c in configs if c.default_model), None) or (configs[0] if configs else None)
if default:
    client = build_model_client(provider=default.provider, model_name=default.model_name,
                                api_key=api_key, base_url=default.base_url)
    agent_manager = AgentManager(mock_mode=False)
    agent_manager.set_model_client(client, stream=True)   # ✅ 真实模式

这就是"重启后端即进入真实对话"的实现：settings.mock_mode 不是 True 时，只要库里有默认模型且能解密 Key，就构建 AG2 客户端进入真实模式；否则安全回退 mock。构建函数 build_model_client()（agent_manager.py）：Anthropic 走原生 AnthropicChatCompletionClient（缺依赖则回落），其余全部走 OpenAIChatCompletionClient —— 任意 OpenAI 兼容端点（DeepSeek / Moonshot / 自建 vLLM）都能接。

per-agent 模型覆盖（成员级绑定）

  • 每个成员在 member_profiles.model_id 存一个模型配置 id（成员管理里切换模型 → 写这个字段 → 审计日志）。
  • 运行时：_build_agent_instance() 取 client = agent_model_clients.get(agent_id) or model_client —— 有覆盖用覆盖，没有用全局默认。
  • 关键细节：has_override = agent_id in agent_model_clients，只要存在 per-agent 覆盖，即使 Manager 处于 mock 模式也强制真实模式（用户明确给这个成员绑了模型，就尊重它）。

重启恢复绑定

lifespan 里有一整段"Re-apply per-agent model bindings"：查询所有 MemberProfile.model_id 非空的成员 → 逐个解密 Key → build_model_client() → 写入 agent_model_clients[agent_id] → rebuild_agent(agent_id) 重建 AG2 Agent 实例。所以重启后每个成员的模型绑定自动恢复，不需要重新配置。

两层绑定：启动时检测默认模型构建全局客户端；重启时按 member_profiles.model_id 恢复每个成员的专属模型客户端。
学习要点：这套设计的核心是"配置与运行时解耦" —— 配置中心只管"记"，AgentManager 只管"取"。任何模块要 Key 就调 get_decrypted_key()，要客户端就调 build_model_client()，新增模型类型不需要动业务代码。

与业内对比评分

参照 LiteLLM Proxy（业界最流行的 LLM 网关）与 One API（国内开源网关），按"个人学习项目目标"评分：

维度做了什么业内参照评分差距与改进
多类型管理 llm / embedding / vision / search / code 五类一张表，每类一个默认，前端 Tab 分栏管理 LiteLLM model_list / One API 渠道 4.0 ★ 分类建模完整；缺模型健康状态自动检测、批量导入（yaml/json）
加密存储 Fernet 对称加密 + 主密钥持久化（.master_key / env）+ api_key_hash 脱敏展示，明文只在内存 LiteLLM（master_key / 数据库加密）/ Vault 4.2 ★ 示范了正确原则；缺 KMS 托管、密钥轮换、审计式解密日志
测试连接 LLM chat.completions 实测 + Embedding 双路径（OpenAI 格式 vs DashScope 专用端点），返回延迟 LiteLLM /test、One API 测试渠道 3.8 ★ 功能到位；缺批量并发测试、延迟/成功率统计曲线
限流执行 rpm/tpm/tpd 字段已建模、前端可填，但未在请求路径强制执行 LiteLLM 路由限流 / One API 令牌桶 2.0 ★ 诚实短板：需在 build_model_client 外层加令牌桶中间件，或直接接入 LiteLLM 做转发
自动路由 启动自动检测默认模型；per-agent 绑定可覆盖；无故障转移 LiteLLM 多模型路由 / 故障切换 / 负载均衡 2.5 ★ 绑定语义真实；缺同一类型多模型间的自动路由、失败重试到备用模型
总体：3.3 / 5.0 —— 管理与加密维度做得好（学习级里少见地完整），限流执行与自动路由是刻意留白：前者可以作为一个很好的"给项目加中间件"的练手题，后者是接 LiteLLM 的自然演进。
