🔍 复盘：单一数据源「双轨制」问题

2026-08-25 · 同一天内两次踩中同一架构病 · 关联 commit：7631891 / 510bb97 / 3b1b50b

一句话总结：同一个能力在系统里存在两套互不同步的实现/定义，一份是精心维护的"管理面"，另一份是实际生效但劣化的"运行时"——单一数据源原则被破坏。今天它以两种形态各爆了一次：上午是工具 schema 双轨制（用户聊天收到裸 JSON），下午是嵌入调用双轨制（改配置必坏一边）。

一、案例一：工具 Schema 双轨制（裸 JSON 事故主因之一）

现象

问可灵「你能看时间吗」，返回 {"success": true, "datetime": ...} 裸 JSON；此后多轮对话、跨 Agent 反复复现。

双轨在哪

A 轨（管理面）B 轨（运行时）
载体ToolRegistry + ToolParameter（手写元数据）AG2 FunctionTool 从函数签名自动推断
内容完整：enum、参数描述、类型劣化：action: string，enum 和描述全丢
消费者前端工具箱 UI、API 展示模型（真正重要的消费者）

根因代码：get_ag2_tools() 构造 FunctionTool 时只传了 func/name/description，而该版本 AG2 的 FunctionTool 没有 schema 参数，只能从贫瘠的签名推断 → 模型看不到 enum，瞎猜 action="get_current_time"。叠加 AG2 默认 reflect_on_tool_use=False（工具结果不转述直接回显），最终把错误 JSON 原样发给用户。

ToolParameter(enum+描述) ──✗ 未传递 ──→ 模型
        │                                    │
        ▼ 管理面展示                          ▼ AG2 从签名推断（劣化）
   前端工具箱显示正常              模型瞎猜参数 → 错误JSON → 回显给用户

修复（commit 510bb97）

  • 合轨：内置工具函数签名改用 Literal["now","format","parse"] + Annotated[...]，让 AG2 自动生成的 schema 天然携带 enum 与描述——签名即唯一真相，两轨同源永不漂移；
  • 补翻译层：显式传 reflect_on_tool_use=True，工具执行后强制二次推理转述为自然语言；
  • 防御兜底：_real_stream 检测疑似裸 JSON 的 fallback 内容，绝不直通用户；
  • 策略护栏：注入 TOOL_USE_POLICY（寒暄不调工具、禁止直发 JSON）；
  • 记忆治理：_is_memory_noise 写入守卫 + 存量清理，切断"错误自强化回路"。

二、案例二：嵌入调用双轨制（改配置必坏一边）

现象

embedding 配置有两个消费方，协议需求"相反"：

消费方实现方式对 base_url 的要求
RAG 知识库模块自带 DashScopeEmbeddingProvider（DashScope 原生协议）必须以 /api/v1 结尾（URL 拼接逻辑决定）
记忆系统 vector_memory标准 OpenAI SDK（兼容协议）必须是 /compatible-mode/v1

一份配置喂两个胃口相反的消费方 → 把配置改成 compatible-mode 时记忆系统好了、RAG 会拼出 .../compatible-mode/v1/api/v1/services/... 这种坏 URL 直接挂掉。

事后复盘确认：两个模块都是近期开发，分叉的唯一原因是开发时对接了不同的模型服务——不是有意设计，也没有历史包袱。这正是双轨制的典型成因：各自独立实现、互不知晓、无同步机制。

修复（commit 3b1b50b）

  • _is_dashscope_model() 增加 compatible-mode 排除判断——检测到兼容模式 URL 一律路由到 OpenAIEmbeddingProvider；
  • OpenAIEmbeddingProvider 增加 20 条/批分批处理（DashScope 兼容模式批次上限）；
  • 架构决策（经六维评估 + 实测）：统一走 OpenAI 兼容模式为主线；DashScopeEmbeddingProvider 保留为未来混合检索的可选适配器，通过 Provider 工厂按需路由。

三、附赠发现：字段名不匹配的静默失败

实施配置切换时还挖出第三个 bug：update_model_config 服务层检查的是 ORM 列名 default_model，而 API 层传入的字段名是 is_default → setattr 设置了不存在的属性，"设为默认"功能一直静默失败（这也解释了为什么 embedding 配置一直没被设成默认）。已在服务层做字段归一化修复。

这类 bug 的共同特征：不报错、不崩溃、只是悄悄不生效。比崩溃更危险，因为它会让人误以为"配置过了就是生效了"。识别手段：任何配置类改动都要做一次端到端验证（读回状态确认），而不是只看接口返回 200。

四、方法论沉淀

#教训落地做法
1单一数据源原则：同一能力的定义/实现只允许存在一份，其他视角从它派生工具定义以函数签名为唯一真相；嵌入调用统一 Provider 工厂
2框架默认值 ≠ 产品假设：关键行为必须显式声明，不依赖第三方隐式默认reflect_on_tool_use=True 显式传入
3schema 质量 > 模型选择：实测证明劣化 schema 下 MiMo 和 Qwen 都会瞎猜参数enum/描述必须写入签名注解，永远不指望模型兜底
4以事实为依据：文档说"仅原生支持"不代表真的不支持（instruct 实测可用，官方文档过时）判定实验法：对比加参前后向量差异，而非只看 HTTP 200
5记忆需要内容治理：无差别落库会让记忆系统变成错误放大器写入守卫过滤噪声 + 存量清理脚本

五、预防清单（新代码评审时自查）

  • □ 这个能力是否已有实现？有 → 复用或合并，而不是再写一份；
  • □ 同一份数据/配置是否有多个消费者？列出所有消费者并确认需求一致；
  • □ 依赖的框架默认值是什么？是否与产品预期一致？显式传参了吗？
  • □ 配置改动后，是否做了端到端读回验证？
  • □ 新增的自动生成逻辑（schema/序列化），生成结果是否人工核对过一次？
