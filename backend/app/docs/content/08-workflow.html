为什么需要工作流编排

对话式多 Agent 协作（私聊 / 群聊）解决的是"一次交互"的问题：你 @ 一个 Agent，它调用工具、给出回答。但真实世界的任务往往是多步骤、有依赖、可重复的：

  • 多步骤："调研一个主题" ≠ 一次问答，而是「搜索信息 → 提炼分析 → 生成报告」三步，每步的输出是下一步的输入。
  • 有分支："发布内容" 需要先判断是否敏感——敏感走人工审核，不敏感直接发布，两条路必须二选一。
  • 可重复：同一套流程要反复跑（每周调研、每次发版前代码评审），每次手打 prompt 不可持续。
  • 可审计：跑完要知道每一步谁执行的、输入输出是什么、耗时多久、失败在哪。

工作流编排的价值就是把「执行过程」从人脑里搬到可建模、可运行、可回放的图里：节点是"做什么"，连线是"依赖与分支"，引擎负责把图跑起来。

💬 对话编排（已有）

  • 由 AG2 GroupChat 驱动，语义是"谁跟谁聊"
  • 适合开放探索、头脑风暴
  • 流程隐含在对话轮次里，不可复现

🌿 工作流编排（本篇）

  • 由自研 DAG 引擎驱动，语义是"先做什么、再做什么"
  • 适合固定流水线、可复用任务
  • 结构显式、可保存、可回放、可可视化
两者互补：对话编排负责"灵感的涌现"，工作流编排负责"流程的确定性"。业界（n8n / Dify / Flowise）的成熟形态正是把后者做成可视化画布，这也是本项目工作流的优化方向。

DAG 数据模型

优化把旧的「链式字段」（next_step_id / then_step_id / parallel_step_ids / depends_on 四套连接描述）统一为一张 有向无环图（DAG）：节点（Node）表达"做什么"，连线（Edge）表达"依赖与分支"。数据类定义在 backend/app/workflow/engine.py：

两个核心数据类

@dataclass
class WorkflowNode:          # 一个节点
    id: str                  # 唯一 id（前端 React Flow 同 id）
    name: str                # 展示名
    node_type: StepType      # agent_call / tool_call / condition / transform / human_review
    config: Dict             # 类型专属配置（agent_id、tool_name、expression、template…）
    position: Dict           # 画布坐标 {"x": 0, "y": 0}（持久化后布局不丢）
    # 运行时字段（每次运行 reset）:status / input_data / output_data / error / duration_ms

@dataclass
class WorkflowEdge:          # 一条有向连线
    id: str
    source: str              # 源节点 id
    target: str              # 目标节点 id
    source_handle: str       # "success" | "failure" | "always"
    condition: str           # 条件表达式（如 data["result"] == true），可空

触发模型（trigger model）

  • 种子节点：没有入边的节点是执行起点，拿到 initial_input 直接跑。
  • 出边触发：节点完成后，逐条检查出边——source_handle 匹配（成功/失败）且 condition 求值为真，就触发目标节点；多条出边同时满足则并行执行（asyncio.gather）。
  • 输入合并：单边到达的节点直接收到源节点输出；多边到达的节点收到 {"源id": 输出, ...} 字典。
  • 未触达即跳过：条件分支未走的一侧保持 pending，运行结束统一标记为 skipped，不会误判失败。
「内容审核发布」模板的 DAG：条件节点用两条带 condition 的出边表达分支，未走的一侧最终标记 skipped。
为什么用"边上的条件"而不是"节点里的 then/else 字段"？因为一条连线一个条件是 DAG 的统一原语：顺序 = 无条件边，分支 = 条件边，并行 = 多条同时满足的边。所有拓扑（顺序/并行/条件/审批）用同一套数据结构表达，引擎只需处理"边是否满足"。

安全表达式求值器 evaluate_condition

条件节点允许用户写表达式控制分支，但不能执行任意代码。实现思路（engine.py 第 231-279 行）：

  • 用 ast.parse(expr, mode="eval") 把表达式解析成 AST，然后 ast.walk 逐个节点校验类型，只放行 _ALLOWED_AST 白名单（比较、算术、布尔、成员判断、下标等）。
  • 禁止 __ 开头的属性访问（防绕过），未知名字（ast.Name 不在 _ALLOWED_NAMES）直接拒绝。
  • 求值时注入 __builtins__ = {}（清空内建函数），只暴露 data / input / ctx 三个数据名字。
evaluate_condition('data["score"] > 0.5', {"score": 0.8})   # → True
evaluate_condition('"敏感" in data["response"]', {"response": "无敏感内容"})  # → False
evaluate_condition('__import__("os").system("rm -rf /")', {})  # → False（白名单拒绝）

agent_handler 如何工作

async def agent_handler(input_data, config):
    agent_id = config.get("agent_id")
    prompt = config.get("prompt", "")
    message = _stringify(input_data)
    if prompt:  # prompt 支持 {{ }} 模板
        message = render_template(prompt, input_data, {}) + "\n\n" + message
    return {"response": await agent_manager.send_message(agent_id, message)}

tool_handler 如何工作

async def tool_handler(input_data, config):
    tool_name = config.get("tool_name")
    params = dict(config.get("params") or {})
    for k, v in list(params.items()):
        if isinstance(v, str) and "{{" in v:   # 参数也支持模板
            params[k] = render_template(v, input_data, {})
    result = tool_registry.execute(tool_name, **params)
    return {"result": result, "tool": tool_name, "params": params}
诚实说明设计取舍（对应计划文档 3.1）：计划里提过 config.mock = true 的节点级开关，最终实现采用更简单也更透明的方案——五类 handler 无条件注册，引擎层永远走真实路径；是否"真实"取决于 AgentManager 自身的 mock 兜底（没配模型时 send_message 返回模拟回复）。好处是引擎逻辑单一；代价是节点级"强制模拟"不可单独开关。另外 agent_call 是同步取完整回复而非流式，稳定性优先，流式吐字到画布留作增强项。

SQLite 持久化

优化前的数据都在内存 dict 里，重启即丢。现在定义与运行历史都落 SQLite（表定义在 backend/app/models/__init__.py 第 210-240 行）：

持久化路径：定义与每次运行都写库；启动时 load_from_db() 把定义载回内存，并回填 run_count / last_run_status。
  • 写定义：_persist_workflow 把节点/连线序列化成 definition_json，插入或更新 workflow_defs（幂等：有则更新，无则新增）。
  • 写运行：_persist_run 每次执行结束把 WorkflowRun（含每步状态 steps_json）插入 workflow_runs。
  • 读历史：get_runs(workflow_id, limit) 按 created_at 倒序返回，前端「运行历史」面板展示。
  • 启动加载：load_from_db() 遍历 workflow_defs，用 _from_dict 重建 Workflow 对象；顺带查出每个工作流最近一次运行回填统计字段；坏数据（JSON 解析失败）跳过并打印告警。
set_db(get_db) 传入的是 FastAPI 的 get_db（生成器工厂），_get_session() 做了兼容处理：如果工厂返回的是可迭代生成器就 next() 取出 session，普通工厂则直接用——这是把 FastAPI 依赖注入风格接进普通类的常见小技巧。

React Flow 可视化编辑器

前端用 @xyflow/react（React Flow v12）实现画布式编排器（frontend/src/components/workspace/workflow/WorkflowEditor.tsx），布局与 n8n / Dify 同构：

编辑器三段式布局：顶部工具栏 → 左工具箱 + 中央画布 + 右属性面板。节点/连线状态与后端 Workflow.to_dict() 双向同步。

关键交互实现

  • 节点渲染：自定义 WorkflowFlowNode 组件（第 81 行起），按 NODE_TYPE_META 取颜色与文案，左右各一个 Handle 端口用于连线。
  • 条件连线自动生成：onConnect（第 335 行起）检测到源节点是 condition 时，自动把 sourceHandle 定为 true/false 并写入 condition: 'data["result"] == true|false'，用户不用手写表达式。
  • 双向转换：toFlowNode / fromFlowNode / fromFlowEdge 在 React Flow 节点结构与后端 DAG 结构之间互转（保存时剔除运行时字段）。
  • 运行即保存：handleRun 先 handleSave() 把当前画布落库再执行，保证"执行的定义 = 眼睛看到的画布"；后台执行 + 每 1.2s 轮询 /api/workflows/{id} 同步节点状态（syncRunState）。
运行态五色（与前端 STATUS_META 一致）：执行时画布节点实时高亮，点节点看输入/输出/耗时/错误——学习导向的"过程可见"。

对比评分:n8n / Dify / Flowise

工作流编排的业内参照是 n8n（代码优先的可视化自动化）、Dify（LLM 应用平台）、Flowise（拖拽式 LLM 编排）。评分原则：功能完整性 × 实现深度 × 生产就绪度，1-5 星。

五维度自评：DAG 建模与 SQLite 持久化做得扎实；并行分支虽有（多出边 + gather），但缺并行度控制与合并语义。
维度做了什么n8nDifyFlowise本项目
编排模型节点 + 连线 DAG，边条件表达分支，多出边并行5.0 ★4.5 ★4.0 ★4.0 ★
真实执行五类 handler 接 AgentManager / ToolRegistry / 审批，mock 透明兜底5.0 ★4.5 ★4.0 ★3.6 ★
持久化workflow_defs / workflow_runs 双表，启动回填统计，历史可查5.0 ★4.5 ★3.5 ★4.4 ★
可视化React Flow 三栏编辑器、运行态五色高亮、运行历史面板5.0 ★4.0 ★4.0 ★4.3 ★
并行分支多出边同时满足即 asyncio.gather；缺并行度上限、join 合并、错误重试5.0 ★4.0 ★3.5 ★3.5 ★
结论：工作流模块在本项目中属于亮点模块——DAG 建模、真实执行接线、SQLite 持久化、React Flow 编辑器形成了完整闭环，面试叙事强（"我用 React Flow 实现了可视化 DAG 工作流编排器，每一步真实调用 AG2 Agent 和内置工具"）。与 n8n 的差距主要在工程深度：无并行度控制、无失败重试策略、无版本控制、无跨工作流调用。
