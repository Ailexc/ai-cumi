为什么要追踪 Agent 执行

Agent 是一个黑盒：你发一句话，等几秒，收到一段回复。但中间发生了什么？模型被调了几次？工具是否真的执行了？哪一步最慢？出错了到底错在哪？——如果这些不可见，出了问题就只能靠猜。

一次普通回复背后可能发生的事

  • 检索长期记忆（memory_query）——可能慢，可能返回一堆无关内容
  • 调用大模型（model_call）——可能超时、重试、流式中断
  • 执行工具（tool_call）——可能抛异常、返回脏数据
  • 多轮 Agent 循环——同一回复可能多次模型调用

业界早有共识：LangSmith / Langfuse / AgentOps 等可观测平台的立身之本，就是把这些"看不见的执行"变成"看得见的 Trace 链"——一次请求生成一条 Trace，Trace 里挂一串带耗时的事件，前端可视化回放。AiCumi 的 TracingSystem 以学习级规模复刻了这套模型：

  • 事件全记录：agent / tool / model / memory / error 五类事件，每件带时间戳与耗时。
  • Trace 生命周期：一次执行一个 Trace（start → 事件流 → end），可回查。
  • 实时推送：事件通过 WS trace.event 实时推到前端面板，边跑边看。
  • 性能统计：跨 Trace 聚合 avg / p50 / p95 / max、调用次数与错误率。
学习要点：可观测性的本质是「在关键路径上打点 + 用统一模型承载 + 让数据可查询可视化」。理解 Trace/Event/Span 三元模型，就理解了 LangSmith 这类产品的骨架。

TracingSystem 事件模型

核心实现 backend/app/tracing/tracer.py，三个数据类构成模型：TraceEventType（事件类型枚举）、TraceEvent（单条事件）、Trace（一次执行的容器）。全局单例 tracing_system 由 backend/app/tracing/__init__.py 导出。

TraceEventType 事件类型

事件类型含义当前接线状态
agent_start / agent_endAgent 执行开始 / 结束枚举预留（DM 路径以 start/end trace 表达）
tool_call / tool_result工具调用 / 工具返回trace_tool_call() 上下文管理器自动成对产出
model_call / model_response模型请求 / 响应DM 路径在真实模式下打 model_call
memory_query / memory_add记忆检索 / 记忆写入DM 路径命中记忆时打 memory_query
approval_request / approval_resolved审批发起 / 解决与 HITL 系统联动预留
error执行异常工具异常时带 parent_id 关联失败的工具事件
custom自定义业务事件扩展点，任意数据均可承载

TraceEvent 的关键字段是 parent_id 与 duration_ms：parent_id 把"工具调用 → 工具异常"这类从属关系串成树，duration_ms 让"哪一步慢"一目了然。

Trace 生命周期

一条 Trace 的事件链：agent_start → memory_query → model_call → tool_call → tool_result。每条事件带耗时，瓶颈一眼可见。
# backend/app/tracing/tracer.py · 生命周期骨架
trace = tracing_system.start_trace(agent_id, {"kind": "dm_stream", "message": msg[:200]})
try:
    await tracing_system.add_event(trace.id, TraceEventType.MEMORY_QUERY, agent_id, {...})
    await tracing_system.add_event(trace.id, TraceEventType.MODEL_CALL, agent_id, {...})
    ...
finally:
    tracing_system.end_trace(trace.id)   # 无论成败都收尾

每条事件最终序列化为这样的 JSON（TraceEvent.to_dict()），前端面板与 API 消费的是同一结构：

{
  "id": "8f2a...",                       # 事件自身 id
  "trace_id": "c1e9...",                 # 所属 Trace
  "event_type": "tool_call",             # 事件类型
  "agent_id": "keling",                  # 哪个员工
  "timestamp": "2026-08-22T10:15:32.118",
  "data": {"tool": "web_search", "params": {"query": "AG2 最新版本"}},
  "parent_id": null,                     # 异常事件会指向父 tool_call
  "duration_ms": 850.3                   # 该步骤耗时（毫秒）
}
注意 finally 里的 end_trace：异常也要关闭 Trace，否则它会永远挂在"进行中"列表里。这个细节保证 get_stats() 的耗时样本不被泄漏的 Trace 污染。

埋点位置：五类入口

埋点散落在 backend/app/agents/agent_manager.py 的 send_message（DM 非流式）与 stream_message（DM 流式）两个主入口，工具执行则有专门的上下文管理器。五类入口与落点：

入口埋点内容代码位置
DM 对话（非流式）start_trace(kind=dm) → 命中记忆打 memory_query → 真实模式打 model_call → end_traceagent_manager.send_message
DM 流式（WS）同上，kind=dm_stream，记忆哨兵 __MEMORY__ 前打 memory_queryagent_manager.stream_message
群聊 / 路由经 @路由后复用 DM 路径，同一套埋点GroupChatManager → 转发 send_message
工具执行trace_tool_call 上下文管理器：进 → tool_call；出 → 写 duration_ms（即 tool_result）；异常 → error（带 parent_id）tracing_system.trace_tool_call
记忆检索 / 写入memory_query（检索条数）/ memory_add（写入）DM 路径随记忆链路触发
埋点地图：AgentManager 主路径负责开/关 Trace 与记忆/模型事件，工具执行用上下文管理器成对埋点，TracingSystem 统一存储并实时推送。
# backend/app/tracing/tracer.py · trace_tool_call（成对埋点 + 异常挂接）
@asynccontextmanager
async def trace_tool_call(self, trace_id, agent_id, tool_name, params):
    start_time = time.time()
    event = await self.add_event(trace_id, TraceEventType.TOOL_CALL, agent_id,
                                 {"tool": tool_name, "params": params})
    try:
        yield event
    except Exception as e:
        await self.add_event(trace_id, TraceEventType.ERROR, agent_id,
                             {"error": str(e), "tool": tool_name},
                             parent_id=event.id if event else None)  # 挂到失败的调用上
        raise
    finally:
        event.duration_ms = (time.time() - start_time) * 1000       # 返回即 tool_result

DM 主路径的接线同样直白——send_message 里开 Trace、按分支打事件、finally 收尾：

# backend/app/agents/agent_manager.py · send_message 埋点（要点）
trace = tracing_system.start_trace(agent_id, {"kind": "dm", "message": message[:200]})
try:
    if memories:                                   # 记忆命中才打点
        await tracing_system.add_event(
            trace.id, TraceEventType.MEMORY_QUERY, agent_id,
            {"count": len(memories)},
        )
    if agent_info.get("mode") == "real" and self.agent_instances.get(agent_id):
        await tracing_system.add_event(
            trace.id, TraceEventType.MODEL_CALL, agent_id,
            {"mode": "real", "message": message[:100]},
        )
        return await self._real_respond(agent_id, enriched)
    return await self._mock_respond(agent_id, enriched)
finally:
    try:
        tracing_system.end_trace(trace.id)
    except Exception:
        pass
埋点设计原则：事件按需打、数据裁剪——只打"有信息量"的事件（记忆命中才 memory_query，真实模式才 model_call），消息截断到前 100-200 字符。避免为每条消息塞满原始数据导致 Trace 膨胀。

性能统计：avg / p50 / p95 / max

单个 Trace 只回答"这次发生了什么"；get_stats() 回答"系统整体表现如何"。它把已完成 Trace 的耗时汇总成分布指标，并对全部事件做分类计数——这是把"日志"升级为"监控"的关键一步。

# backend/app/tracing/tracer.py · get_stats 返回结构（要点）
{
  "active_traces": 2, "completed_traces": 46, "total_events": 318,
  "response_time_ms": {          # 已完成 Trace 的端到端耗时分布
    "avg": 4120.5, "p50": 3980.0, "p95": 8120.3, "max": 15302.1,
    "sample_count": 46,
  },
  "calls": {"model_calls": 52, "tool_calls": 31, "memory_queries": 44},
  "errors": {"error_events": 3, "error_rate": 0.94},   # 错误事件 / 总事件
  "agents": { ... },             # 按 agent 聚合：trace 数、调用数、平均耗时
}
统计管线：事件流 → 分位聚合 → 三张指标卡（耗时分布 / 调用次数 / 错误率），前端统计面板直接渲染。

分位数的实现值得注意——pct() 是一个 20 行的小函数：对耗时排序后按下标取分位，p50 是"一半请求比它快"，p95 是"95% 的请求比它快"。它比 avg 更能暴露尾部延迟（个别超慢请求会把平均值拉高，但 p50 不受影响）。

局限要讲清楚：统计只覆盖进程内的 Trace（最多保留 100 条完成记录），没有采样、没有时间窗口聚合、没有持久化——重启即清零。这是学习级与 Langfuse 这类产品的分水岭。

前端追踪面板

追踪面板 frontend/src/components/workspace/TracingPanel.tsx 提供三层信息，数据全部来自 /api/tracing/*：

  • 统计卡片：GET /api/tracing/stats → 平均耗时、模型调用、工具调用、记忆查询（PerfCard 组件）、错误率。
  • 追踪列表：GET /api/tracing/traces → 每条 Trace 显示 agent、开始时间、事件数、总耗时，支持按 agent 过滤。
  • 事件详情：GET /api/tracing/traces/{trace_id} → 展开事件链，每种类型有专属图标与配色（memory_query 数据库图标青色、tool_call 扳手、error 红色告警等），逐条看 data 载荷与耗时。

事件类型 → 图标/配色映射（TracingPanel.tsx）

事件类型图标配色
memory_query数据库青色
memory_add数据库绿色
tool_call / tool_result扳手 / 对勾靛蓝 / 绿色
model_call / model_response芯片琥珀
error告警三角红色

同一事件类型在列表与详情中复用同一映射，扫一眼颜色就能定位异常链。

实时回放怎么来？

与审批面板同款机制：add_event() 时经 _ws_notifier 推 trace.event 事件（含 trace_id 与事件本体）。正在执行的 Trace 会在面板上"边跑边长"，观察者能实时看到模型调用、工具执行的先后顺序——这是 Debug Agent 行为最直观的方式。

调试场景示例：用户说"回答很慢"。打开追踪面板，如果 model_call 占 80% 耗时，是模型慢；如果 tool_call 后面跟着一条 error，是工具挂了被吞进回复——没有 Trace，这两类问题都只能靠猜。

对比评分：LangSmith / Langfuse

业内参照：LangSmith（LangChain 官方观测平台）与 Langfuse（开源 LLM 可观测性，Trace/Observation/Score 模型）。评分原则：功能完整性 × 实现深度 × 工程化 × 生产就绪度，1-5 星。

维度本项目做了什么业内参照评分差距与改进
事件覆盖 agent / tool / model / memory / error 五类事件，工具异常挂 parent_id，WS 实时推送 LangSmith / Langfuse 全链路 Span 4.0 ★ 对话链路覆盖全；群聊/工作流/审批事件尚未全部接线（枚举已预留）
耗时统计 avg / p50 / p95 / max + 调用次数 + 错误率 + 按 agent 聚合 Langfuse 时间序列 + 成本曲线 3.8 ★ 统计维度对；缺时间窗口趋势、对比基线、阈值告警
分布式传播 进程内 trace_id 关联，无跨进程/跨服务上下文传播 OpenTelemetry trace context 传播 1.5 ★ 最大短板：分布式 Worker 的执行未接入统一 Trace；可加 traceparent 头透传
成本归因 记录 model_call 事件，但未统计 token 用量与费用 Langfuse token 计数 + 按模型计价 2.0 ★ 可在 model_response 事件里补 usage 字段，乘单价即得成本
总体：3.2 / 5.0 —— 事件模型与统计口径对齐了业界范式，作为学习项目"形神兼备"；差距集中在工程面：无采样、无持久化、无分布式上下文传播、无成本归因。改进路线：加 usage → 加时间窗口 → 加 OTel 上下文。

学习路径

  1. 先在 send_message 里跑一次带记忆的对话，打开 /api/tracing/traces 看事件顺序。
  2. 给一个工具传入会抛错的参数，观察 error 事件如何通过 parent_id 挂在 tool_call 下。
  3. 读 get_stats() 的 pct()，动手算一组样例数据的 p50/p95，理解分位与均值的区别。
  4. 在 trace_tool_call 里加一个 MODEL_CALL 事件，看面板统计的 model_calls 是否 +1——埋点就是这么简单。
  5. 自问三个面试题：Trace 与 Span 什么关系？怎么加成本归因？分布式下 trace_id 怎么传播？
一句话总结：可观测性 = 统一事件模型（Trace/Event）+ 关键路径埋点 + 分位统计 + 实时可视化。它把 Agent 从"黑盒"变成"可回放、可定位、可量化"的透明系统。
