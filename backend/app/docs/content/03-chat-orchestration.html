功能概览:IM 化多 Agent 对话

对话与编排是 AiCumi 的「门面层」—— 用户打开界面看到的所有聊天能力都来自这一层。它的设计目标是把 AG2 的「Agent 执行原语」翻译成「IM 产品语义」:模型输出是一串 token,产品要把它变成"像微信一样"的对话体验。

这一层由四个模块协作完成(都在 backend/app/ 下):

  • agents/agent_manager.py —— AgentManager:创建/管理 AG2 Agent、real/mock 双模式、流式产出;
  • chat/websocket_manager.py —— WebSocketManager:维护连接集合、收发 JSON 协议消息;
  • services/message_store.py —— MessageStore:消息落库与历史回放;
  • main.py 的 /ws 处理器 —— 协议编排中枢:把 WS 事件翻译成对 Agent 的调用、把流式结果翻译回 WS 事件。
能力一句话实现代码落点关键事件 / 协议
私聊一个 Agent 对应一个房间,room_id = agent_idmain.py /ws 的 chat.send 分支chat.chunk / chat.done
群聊GroupChatManager 维护房间与成员,按 @ 路由响应者agent_manager.py GroupChatManagergroup.create / group.add-member
流式输出AG2 on_messages_stream 逐 token 产出,WS 逐字转发AgentManager.stream_message()chat.chunk(打字机效果)
思考剥离剥离推理内容(前缀/标签两种格式),只推最终答案AgentManager._real_stream() / _strip_reasoning_chunk()chat.thinking 指示器
持久化SQLite messages 表,历史 200 条回放services/message_store.pychat.history

💬 私聊:像和同事 IM

  • 房间即 Agent:room_id == agent_id,点谁聊谁
  • 对话是持续的,无「新建对话」机器范式
  • 支持记忆注入(chat.memory 展示检索到的长期记忆)

👥 群聊:一个群、多个员工

  • 选成员建群,指定群主(默认响应者)
  • @成员 精准路由;不 @ 则由群主值班
  • 每个响应 Agent 独立 messageId,各自流式渲染
核心设计:框架提供「执行原语」,产品提供「编排语义」。AG2 管"Agent 怎么跑",AiCumi 管"谁跟谁聊、聊完怎么存、怎么流式呈现、怎么剥离思考"。

Agent 生命周期:创建与 real/mock 双模式

每个「员工」(可灵 / 小研 / 小码…)在 AgentManager 里对应两条记录:一份元数据(存在 self.agents[agent_id] 的 dict 里)和一份实例(存在 self.agent_instances[agent_id],真实 AG2 Agent 或 None)。

创建:create_agent()

create_agent()(backend/app/agents/agent_manager.py)先把元数据落盘到内存 dict,再走统一的 _build_agent_instance() 构建真实实例,最后根据实例是否为 None 标记 mode:

async def create_agent(self, agent_id, name, persona, role="assistant",
                       tools=None, model_key=None, force_real=False):
    if agent_id in self.agents:
        raise ValueError(f"Agent {agent_id} already exists")
    self.agents[agent_id] = {
        "id": agent_id, "name": name, "persona": persona, "role": role,
        "tools": tools or [], "is_active": True,
        "force_real": force_real, "mode": "mock",
        # ... created_at / updated_at ...
    }
    agent_instance = self._build_agent_instance(agent_id)
    self.agent_instances[agent_id] = agent_instance
    mode = "real" if agent_instance is not None else "mock"
    self.agents[agent_id]["mode"] = mode
    return agent_instance

real / mock 双模式:_build_agent_instance()

构建真实 Agent 需要满足三个条件,_build_agent_instance() 里的判定逻辑是理解整个项目的钥匙:

use_real = (
    HAS_REAL_AGENT                      # ① AG2 包已安装
    and client is not None              # ② 有可用模型客户端(共享或 per-agent)
    and (has_override                   # ③ 该成员显式绑定了模型(强制 real)
         or not self.mock_mode          #    或全局未开 mock
         or info.get("force_real"))     #    或创建时 force_real=True
)
场景结果说明
未配置任何模型启动报错后端明确提示「请在模型管理配置 LLM 模型」，不 mock 兜底
配置默认模型并重启realset_model_client() 挂上共享客户端,model_client_stream=True
成员级模型覆盖强制 realagent_model_clients[agent_id] 存在时走该成员绑定的真实模型
force_real=True强制 real创建/更新成员时显式要求真实模式
学习要点:学习项目默认走真实模式,未配置模型时后端明确报错提示,不 mock 兜底——mock 只用于 CI 测试,不掩盖「没配模型」的环境问题。

实例热更新:rebuild_agent()

人设、模型或工具绑定变化后,调用 rebuild_agent(agent_id) 保留元数据、重建底层 AssistantAgent 实例,并同步更新 mode。它是「前端改完点保存 → 后端无缝换 Agent」的开关。

私聊与流式输出

私聊的完整链路跑在 main.py 的 /ws 处理器里(约 578-838 行),一条 WebSocket 连接同时承载指令下发(chat.send)与流式推送(chat.chunk)。协议事件如下:

事件方向含义
chat.send前端 → 后端发消息,携带 roomId / content / mentions / knowledgeScope
chat.memory后端 → 前端检索到的长期记忆(首个 chunk 前发出)
chat.thinking后端 → 前端模型进入推理阶段(UI 显示"思考中…")
chat.chunk后端 → 前端逐 token 正文,前端打字机渲染
chat.done后端 → 前端流结束,携带 fullContent 供前端固化
chat.history请求 / 响应按房间回放历史(默认 200 条)

实现原理:AG2 流式接口

AG2(autogen-agentchat 0.7.5)的 AssistantAgent 在构造时传入 model_client_stream=True,即可用 on_messages_stream() 异步迭代事件流。其中 ModelClientStreamingChunkEvent 是增量 token,最后一个事件是含 chat_message 的完整响应。AgentManager 把这层封装成「带哨兵」的异步生成器 stream_message():

  • __MEMORY__:<json> —— 检索到的长期记忆,WS 层翻译成 chat.memory 事件;
  • __THINKING__ —— 模型进入推理,WS 层翻译成 chat.thinking 事件(只发一次);
  • 其余内容 —— 剥离思考后的正文 chunk,直接转发为 chat.chunk。
私聊流式时序:chat.send → 记忆检索 → on_messages_stream → 思考剥离 → chat.chunk 逐字推送 → chat.done + 落库。
  1. 发送:前端 chat.send 携带房间与内容;若带 knowledgeScope 还会先做 RAG 检索注入上下文。
  2. 记忆检索:build_memory_context() 向量检索长期记忆,以 __MEMORY__: 哨兵先行发出。
  3. 流式:on_messages_stream() 逐 token 产出 ModelClientStreamingChunkEvent。
  4. 剥离与转发:_real_stream() 剥掉推理内容,正文以 chat.chunk 逐字推给浏览器。
  5. 收尾:chat.done 携带完整内容;用户消息与回复分别落库,并把本轮问答写入长期记忆(save_exchange)。

思考剥离:把「想」和「说」分开

推理模型(如 R1 系 / MiMo)会在输出里夹带内部思考过程。直接推给用户既打断体验、又浪费 token、还可能泄露 prompt 内部逻辑。AiCumi 在 _real_stream() 里处理两种格式的思考内容:

格式一:AG2 reasoning 前缀(推理内容通道)

OpenAI 兼容客户端对 R1 系模型会把推理内容放在独立通道:首个推理 chunk 以 " thinking" 开头,推理结束时出现 " response" 标记。_real_stream() 的逻辑:

if first_chunk:
    first_chunk = False
    if content.startswith(" thinking"):
        in_reasoning = True          # 进入推理态,先发 __THINKING__ 哨兵
        yield "__THINKING__"
        content = content[len(" thinking"):]
if in_reasoning:
    if content.startswith(" response"):
        in_reasoning = False         # 推理结束,恢复正文
        content = content[len(" response"):]
    else:
        continue                     # 丢弃推理内容

格式二:MiMo 内联 <think> 标签(跨 chunk 缓冲)

部分模型把思考直接嵌在正文里:<think>...</think>。麻烦的是标签可能被切在两次 chunk 之间(比如 <thin 和 k>...</think>),所以需要状态缓冲。_strip_reasoning_chunk(content, state) 接收一个 tag_state dict:

tag_state = {"open": False, "buffer": ""}   # open: 是否在 think 块内

def _strip_reasoning_chunk(self, content, state):
    out = []
    if state["open"]:                        # 上块未闭合 → 先找 </think>
        idx = content.find("</think>")
        if idx == -1:
            state["buffer"] += content       # 仍在块内,继续缓冲
            return None
        state["open"] = False
        state["buffer"] = ""
        content = content[idx + len("</think>"):]   # 处理闭合后的尾巴
    while True:                              # 本块内可能多次出现 <think>
        o = content.find("<think>", i)
        if o == -1:
            out.append(content[i:]); break
        out.append(content[i:o])
        c = content.find("</think>", o + len("<think>"))
        if c == -1:
            state["open"] = True             # 标签跨 chunk,置 open 等下一块
            state["buffer"] = content[o + len("<think>"):]
            break
        i = c + len("</think>")
    return "".join(out) if out else None

配合逻辑:首次出现 <think> 时发 __THINKING__ 哨兵;整块都是思考的 chunk 返回 None,WS 层 continue 跳过,不产生空消息。非推理模型(两个分支都不命中)内容原样透传。

思考剥离双路径:AG2 前缀模式(丢弃到 " response" 标记)与 MiMo 标签模式(跨 chunk 缓冲剥离)。
为什么值得剥离:① 体验——用户只看到最终答案;② 成本——推理 token 不计入 UI 展示与落库;③ 隐私/安全——不外泄 prompt 内部推理;④ 持久化干净——落库的是"人话"。

群聊编排:@ 路由与群主值班

GroupChatManager(同一文件,agent_manager.py 后半部分)维护群聊房间:成员列表、群主、持久化。它不用 AG2 原生 GroupChat 的 speaker-selection 轮转,而是实现了一套更贴近 IM 的「@ 路由」语义。

房间与成员管理

  • create_group_chat(room_id, name, agent_ids, owner_agent_id):校验成员有效性,写入内存并 _persist_room() 落库;
  • add_member() / remove_member():增删成员并同步持久化;
  • to_room():把内部 dict 转成前端 room.list 的形状(memberAgentIds / ownerAgentId);
  • load_persisted_rooms():启动时从 group_rooms 表恢复房间,已删除的成员会被过滤掉。

核心路由逻辑:_resolve_targets()

def _resolve_targets(self, room_id, mentions):
    members = self.group_chats[room_id]["agents"]
    if mentions:                              # 有 @ → 只回被@者
        targets = [aid for aid in mentions if aid in members]
        return targets if targets else members # @ 了不在群里的 → 全体兜底
    owner = self.group_chats[room_id].get("owner")
    return [owner] if owner and owner in members else members   # 无 @ → 群主值班

流式:stream_send() 逐 Agent 独立 messageId

群聊不推 chat.done —— 因为每个 Agent 的回复是独立消息。前端按 messageId 累积各自的消息气泡。注意群聊流式用 use_memory=False:避免 __MEMORY__ 哨兵污染群协议,记忆注入仅限私聊。

async def stream_send(self, room_id, message, mentions=None):
    for agent_id in self._resolve_targets(room_id, mentions):
        message_id = str(uuid.uuid4())        # 每个响应 Agent 一个独立 ID
        async for chunk in self.agent_manager.stream_message(agent_id, message, use_memory=False):
            yield (agent_id, chunk, message_id)   # WS 层转发为 chat.chunk
群聊 @ 路由:@ 某人只回被@者;不 @ 由群主值班;每个响应 Agent 独立消息。

SQLite 持久化房间:GroupRoom 表

群聊房间存 group_rooms 表(backend/app/models/__init__.py):room_id / name / owner_agent_id / member_agent_ids(JSON 数组)。增删成员时 _persist_room() 覆盖写回;重启时 load_persisted_rooms() 恢复并过滤已不存在的成员。

事件后端动作返回
group.createcreate_group_chat() + _persist_room()room.created
group.add-memberadd_member() + 持久化room.list 刷新
chat.send(群房间)存用户消息 → stream_send() 逐 Agent 流式 → 存各 Agent 回复多路 chat.chunk(各自 messageId)
与 AG2 原生 GroupChat 的差异:原生用 speaker-selection 自动轮转发言,适合「研讨会」;AiCumi 用 @ 路由 + 群主值班,适合「IM 群聊」。代价是放弃了 AG2 内置的群聊状态机,换来了更直觉的产品体验。

消息持久化:历史 200 条

所有消息落在 SQLite 的 messages 表(backend/app/models/__init__.py 的 Message 模型):id / role(user|assistant) / content / room_id / agent_id / timestamp。封装在 backend/app/services/message_store.py,只有三个函数,非常干净:

def save_message(db, room_id, role, content, agent_id=None) -> Message:
    msg = Message(room_id=room_id, role=role, content=content, agent_id=agent_id)
    db.add(msg); db.commit(); db.refresh(msg)
    return msg

def load_history(db, room_id, limit=200) -> List[Message]:
    return (db.query(Message)
            .filter(Message.room_id == room_id)
            .order_by(Message.timestamp.asc())
            .limit(limit).all())

def to_frontend_message(m: Message) -> dict:
    ts = m.timestamp
    if ts.tzinfo is None:
        ts = ts.replace(tzinfo=timezone.utc)
    return {"role": m.role, "content": m.content,
            "timestamp": int(ts.timestamp() * 1000), "agentId": m.agent_id}

落库时机(都在 /ws 处理器里)

  • 私聊:收到 chat.send 先存用户消息(agent_id=room_id),流结束后存 assistant 完整回复,随后 save_exchange() 把问答写入长期记忆;
  • 群聊:存用户消息,再把 stream_send 累积出的每个 Agent 回复分别落库(agent_id=对应成员);
  • 历史回放:前端发 chat.history{roomId},后端 load_history(db, room_id, limit=200) 按时间正序返回,to_frontend_message() 转成前端形状。
学习要点:timestamp 用 UTC 存储,转前端时补时区并换算成毫秒时间戳 —— 这是前后端时间处理的一个典型细节。

对比评分:与 AG2 原生 GroupChat

评分原则:功能完整性 × 实现深度 × 产品体验 × 生产就绪度,1-5 星,参照对象是 AG2 / AutoGen 原生的 GroupChat 编排。

维度做了什么AG2 原生 GroupChat评分差距与改进
IM 体验(@ 路由/值班) @ 提及精确路由、无 @ 群主值班、逐 Agent 独立消息 speaker-selection 自动轮转,无 @ 概念 5.0 ★ 远超原生;缺 @ 全部(@所有人)与提及高亮解析
流式体验 chat.chunk 逐字推送 + chat.thinking 指示器 + 打字机渲染 支持流式但需自行接事件循环 4.8 ★ 已接近原生;缺取消/中断已生成流的指令
持久化 messages 表 + GroupRoom 表,历史 200 条,房间重启恢复 不内置持久化,需自行实现 4.5 ★ 原生没有,属自研加分;缺分页与全文检索
框架依赖深度 深度依赖 AG2 AssistantAgent / on_messages_stream —— 3.0 ★ 引擎耦合是双刃剑:升级 AG2 需跟随其 API 变化
会话上下文管理 无显式上下文窗口裁剪,靠记忆检索兜底 内置 context 管理与 token 控制 2.5 ★ 长对话 token 溢出风险;可引入消息摘要/窗口裁剪
总体评分:4.0 / 5.0 —— 作为"面向 IM 体验的多 Agent 对话层"超过 AG2 原生 GroupChat;作为"生产级编排"在上下文管理与取消语义上仍是学习级。核心结论:用自己的产品语义包住框架的执行原语,是 Agent 应用开发的正确姿势。
