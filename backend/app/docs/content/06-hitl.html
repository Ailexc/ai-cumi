HITL 概念：为什么关键操作需要人审

Human-in-the-loop（HITL，人机回环）指在自动化流程中插入"人类决策点"：Agent 在执行有副作用、不可逆、或有风险的操作前，先停下来征求人的同意，人点头才继续。这是生产级 Agent 的必备能力——一个能自由行动的 Agent，和一个有安全阀的 Agent，可信度完全不同。

为什么 Agent 不能全自动

  • LLM 会犯错：幻觉、理解偏差，把"测试"当成"删除生产数据"。
  • 副作用不可逆：发消息给外部、删除文件、调用付费 API、执行命令——错了难补救。
  • 缺业务上下文：模型不知道"这条消息该不该发"这种隐含规则。
  • 信任建立：人审让用户对 Agent 有掌控感，是产品可信度的基石。

🔴 应该审批的操作

  • 向外部/群聊发送消息（send_message）
  • 文件删除 / 覆盖（file_operation）
  • 工具调用（tool_call）
  • 工作流人工审核节点（workflow_step）

🟢 无需审批的操作

  • 纯问答、信息检索
  • 只读工具（查询天气、搜索）
  • 无副作用的内部计算

业界的主流实现是 LangGraph 的 interrupt（中断-恢复）机制：图执行到 interrupt() 处挂起，把控制权交还外部（人/系统），处理完再 Command(resume=...) 恢复执行。AiCumi 用更贴近业务的形式复刻了这个语义：Agent 发一个审批请求 → 挂起等待 → 人在面板上点通过/驳回 → Agent 被唤醒继续。核心思想完全一致：执行可以在中间暂停，而不是整体取消。

对比项LangGraph interruptAiCumi 审批系统
挂起原语interrupt(payload) 挂起图执行wait_for_approval() await 一个 Future
恢复方式外部 Command(resume=value) 续跑面板 resolve → waiter.set_result() 唤醒
状态表达执行栈状态（checkpoint）显式 ApprovalStatus 状态机 + 历史留痕
产品形态API 级原语，需自建 UI自带审批工作台（待办/历史/统计）
学习要点：HITL 的本质是「中断 + 等待 + 恢复」三件套。实现难点不在"发个请求"，而在异步等待——Agent 的调用栈要能挂起，等一个外部事件（人点击）再精确地继续执行。AiCumi 用 asyncio.Future 解决。

审批系统设计

核心在 backend/app/approval/hitl.py：一个 ApprovalRequest 数据类描述"审什么"，一个 HumanApprovalManager 管理"怎么审、怎么等、怎么唤醒"。全局单例 approval_manager 由 backend/app/approval/__init__.py 导出。

ApprovalRequest 状态机

状态枚举 ApprovalStatus 定义了五个终态/中间态，覆盖"人审"的全部走向：

审批状态机：pending 是唯一中间态，流向通过 / 驳回 / 超时 / 取消四个方向；超时与取消是"无人干预"的兜底出口。

ApprovalRequest 携带审批所需的全部上下文（hitl.py 中定义）：

字段说明
iduuid4，审批句柄，API 按它 resolve
agent_id发起审批的员工（工作流为 "workflow"）
action动作类型：tool_call / send_message / file_operation / workflow_step
description人类可读的描述——审批卡片上人看到的就是它
params结构化参数（如工具入参），供审批者判断
status当前状态（见状态机）
created_at / resolved_at发起 / 解决时间，历史排序依据
response人类的回复理由，随结果回传 Agent
auto_approve_after若开启 auto-approve，N 秒后自动通过

HumanApprovalManager：异步等待与唤醒

三个内部结构是理解这个类的钥匙：

# backend/app/approval/hitl.py · HumanApprovalManager.__init__
self._pending_requests: Dict[str, ApprovalRequest] = {}   # 进行中：id → 请求
self._history: List[ApprovalRequest] = []                  # 已解决：滚动窗口(1000)
self._waiters: Dict[str, asyncio.Future] = {}              # 等待者：id → Future
self._ws_notifier: Optional[Callable] = None               # 实时推送钩子
  1. request_approval(agent_id, action, description, params, timeout, auto_approve)：创建请求入 pending → 通过 _ws_notifier 推 approval.request 事件给前端 → 若 auto_approve=True 则起一个后台任务 _auto_approve_after 定时自动通过。
  2. wait_for_approval(request_id, timeout)：Agent 侧挂起等待。已解决则直接返回；否则创建 asyncio.Future 注册进 _waiters，然后 await asyncio.wait_for(future, timeout)——Future 被 resolve 唤醒，或超时自动置为 timeout。这是整个 HITL 的"暂停/恢复"核心。
  3. resolve_request(request_id, status, response)：人/系统裁决入口。从 pending 弹出 → 写状态/时间/理由 → 入 history（超 1000 条截断）→ 用 waiter.set_result(request) 唤醒等待者 → 推 approval.resolved 事件给前端。

实时通知的接线在 set_ws_notifier()：启动时把 WS 广播函数注入进来（见 backend/app/main.py 启动流程），此后每次请求/解决都会以 approval.request / approval.resolved 事件推给所有在线前端。推送内容就是 ApprovalRequest.to_dict()，前端无需再发 REST 查询即可刷新面板。

# backend/app/approval/hitl.py · 事件推送载荷
# request_approval 内：
await self._ws_notifier({
    "type": "approval.request",
    "request": request.to_dict(),   # 含 id/agent_id/action/description/params
})
# resolve_request 内：
await self._ws_notifier({
    "type": "approval.resolved",
    "request": request.to_dict(),   # 含最终 status / response / resolved_at
})
一次审批的完整生命周期：Agent 发起 → 前端展示 → 人类裁决 → Future 唤醒 → Agent 恢复。超时是无人干预时的兜底出口。

ApprovalRequiredTool 工具包装器

ApprovalRequiredTool 把"需审批的工具"包成一个标准执行入口：先审批、后执行。非通过状态一律不执行真实工具，返回给 Agent 一个可读的错误对象——Agent 能据此向用户解释"操作被拒绝了"。

# backend/app/approval/hitl.py · ApprovalRequiredTool.execute（要点）
request = await approval_manager.request_approval(
    agent_id=agent_id, action=f"tool_call:{self.tool_name}",
    description=self.description, params=kwargs,
    timeout=self.timeout, auto_approve=self.auto_approve,
)
resolved = await approval_manager.wait_for_approval(request.id, timeout=self.timeout)
if resolved.status != ApprovalStatus.APPROVED:
    return {"error": "Action rejected by human",
            "status": resolved.status.value, "response": resolved.response}
result = self.tool_func(**kwargs)          # 审批通过才真正执行
return {"success": True, "result": result, "approval_id": request.id}
设计观察：包装器返回结构化结果而非抛异常——拒绝不是"崩溃"，而是"业务结果"。这让 Agent 能优雅地继续对话（"好的，那我先不执行这个操作"），而不是触发错误重试。

审批 API 一览

管理面在 backend/app/main.py 的 /api/approval/*，配合 WS 实时事件 approval.request / approval.resolved 双通道：查询走 REST，变更即时性靠 WS 推送。

方法 + 路径参数返回用途
GET /api/approval/pendingagent_id?requests[]待审批列表（按创建时间倒序）
GET /api/approval/historyagent_id?, limit=50history[]已解决的历史审批
POST /api/approval/{request_id}/resolvestatus: approved|rejected + response?request人的裁决入口；非法 status 返回 400
GET /api/approval/stats—statspending 数、历史数、进行中请求明细
注意 resolve 的入参只有 approved / rejected 两档——timeout 与 cancelled 是系统内部路径（超时自动置位 / 预留），不开放给人直接操作，避免状态被外部写乱。

工作流集成：human_review 节点

工作流引擎（08 · 工作流编排）在注册处理器时，把 HUMAN_REVIEW 节点接到审批系统（backend/app/main.py · _register_workflow_handlers）。这个节点的语义是"流程到这里必须人点头才往下走"：

# backend/app/main.py · _register_workflow_handlers → human_review_handler
async def human_review_handler(input_data, config):
    from .approval import approval_manager
    request = await approval_manager.request_approval(
        agent_id=config.get("agent_id", "workflow"),
        action="workflow_step",
        description=config.get("description", "工作流执行到人工审核节点"),
        params={"input": input_data, **(config.get("params") or {})},
        timeout=int(config.get("timeout", 3600)),
        auto_approve=bool(config.get("auto_approve", False)),
    )
    wait_timeout = int(config.get("wait_timeout", 3600))
    resolved = await approval_manager.wait_for_approval(request.id, timeout=wait_timeout)
    return {"approval_id": request.id, "status": resolved.status.value,
            "response": resolved.response}
  • 工作流执行到该节点时，request_approval 发出审批（action=workflow_step，agent_id 默认 "workflow"，审批卡片上能看到节点描述和输入数据）。
  • wait_for_approval 让工作流阻塞在节点上，最长 wait_timeout（默认 1 小时）。
  • 审批通过 → 节点返回 {status, response} 给下游；审批拒绝 → 下游节点拿到拒绝结果，可按条件分支处理。
工作流中的审批闸口：执行到 human_review 节点即挂起，通过才放行到工具节点；驳回则把拒绝结果交给下游（可做条件分支或终止）。

前端审批面板

审批面板 frontend/src/components/workspace/ApprovalPanel.tsx 是三段式布局，对应三个 API：

  • 待审批列表：GET /api/approval/pending，每张卡片展示 Agent、动作类型（tool_call / workflow_step…）、描述、参数，右侧「通过 / 驳回」按钮（驳回时可填理由），点击即 POST /api/approval/{id}/resolve。
  • 历史：GET /api/approval/history，带状态徽章（通过绿 / 驳回红 / 超时黄）与解决时间。
  • 统计：GET /api/approval/stats，显示"进行中 N 条 / 已处理 M 条"。

实时性怎么来？

WS 通道订阅 approval.request 与 approval.resolved 事件：新审批到达立即冒泡（带角标提醒），resolve 后自动从待办列表消失、进入历史——无需手动刷新。这也是整个工作流审批"看起来像实时协作"的关键。

对比 LangGraph：它的 interrupt 是"API 层挂起 + 外部用 Command(resume) 恢复"；AiCumi 是"内存 Future 挂起 + 前端面板点按钮恢复"。语义等价，但本项目把恢复动作做成了有 UI 的审批工作台，更贴近企业审批流的产品形态。

对比评分：LangGraph interrupt

业内参照：LangGraph interrupt/Command(resume)（图执行中断-恢复原语）与生产级审批流（工单/审计系统：多级审批、超时升级、留痕）。评分原则：功能完整性 × 实现深度 × 工程化 × 生产就绪度，1-5 星。

维度本项目做了什么业内参照评分差距与改进
机制完整性 完整状态机（pending→approved/rejected/timeout/cancelled）、Future 等待唤醒、工具包装器、工作流节点全打通 LangGraph interrupt / 企业审批流 3.8 ★ 机制闭环成立；缺审批「理由回写模型上下文」（驳回理由应让 Agent 下次避免）

学习路径

  1. 先读懂 wait_for_approval 的 Future 机制：为什么 set_result 能唤醒一个早就 await 的协程？这是 asyncio 面试考点。
  2. 用 ApprovalRequiredTool 包一个工具，在面板上点"驳回"，观察 Agent 拿到的结构化错误。
  3. 在工作流编辑器里加一个 human_review 节点，跑一遍"挂起 → 审批 → 继续"。
  4. 把 wait_timeout 调成 5 秒，观察 timeout 状态落库——超时路径闭环。
  5. 自问三个面试题：中断恢复怎么实现？拒绝后如何让 Agent"长记性"？多级审批链怎么设计？
一句话总结：HITL = 审批状态机 + asyncio.Future 等待唤醒 + WS 实时通知 + 工作流闸口。它是 AiCumi 从"聊天玩具"走向"可信 Agent"的关键一步。
