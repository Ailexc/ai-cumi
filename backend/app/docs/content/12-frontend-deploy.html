前端总体架构：三段式布局

前端是一个 React 19 + Vite 6 + Tailwind CSS v4 的单页应用（依赖 react-router-dom、lucide-react 图标、@xyflow/react 工作流画布等）。整体采用飞书风格的三段式布局：左侧功能导航栏（AppRail）→ 中间列表区 → 右侧主内容区。

布局与交互范式

  • 导航范式而非弹窗：点击左侧功能项 → 右侧主区域切换视图（不是弹层），保持"一个工作台"的心智模型。
  • 持续对话：点团队成员 = 进入与 TA 的持续 IM 对话（没有"新建对话"这种机器范式），与后端 room 模型一一对应。
  • 分层清晰：Workspace 壳（布局与状态）→ Hooks（数据接入）→ 业务视图组件（功能页）。
三段式布局：AppRail（功能导航）| Sidebar（列表）| 主内容区（视图切换）。数据层由 Hooks 统一接入。

WS 协议设计与 useChatSocket

前后端实时通道是 /ws WebSocket，协议是JSON 事件消息（type 字段路由）。前端把整条连接封装成一个 Hook frontend/src/hooks/useChatSocket.ts，对外暴露 connected / rooms / agents / messages / unread / thinking / memories 与发送方法。

事件类型表

方向事件载荷要点说明
客户端 → 服务端chat.sendroomId / content / mentions / knowledgeScope发消息（可携带 RAG 范围，见 10 篇）
chat.historyroomId拉取云端历史（limit 200）
group.createname / memberAgentIds / ownerAgentId创建群聊 → 服务端回 room.created
group.add-memberroomId / agentId拉人进群 → 重发 room.list

服务端 → 客户端agent.list · room.listagents[] / rooms[]连接建立与刷新时的全量快照

chat.chunkroomId / messageId / content / agentId流式逐块内容（打字机渲染）
chat.memoryroomId / messageId / memories[]该条回复关联的长期记忆（可视化）
chat.doneroomId / messageId / fullContent流结束，完整内容落定（群聊无此事件）
chat.errorroomId / error错误提示（同时清除 thinking）

Hook 的三个关键设计

  • handlerRef 模式：消息处理器放在 useRef 里，每次渲染更新 handlerRef.current —— 避免 useEffect 依赖链问题，连接只建一次（useEffect(..., [])）。
  • 流式累积：streamingRef: Map<"roomId:messageId", string> 累积 chunk，chat.chunk 时把最新内容 merge 进对应消息；chat.done 时用 fullContent 替换并置 streaming: false。
  • 未读角标：unread[roomId] 只在非活跃房间收到新 assistant 消息时 +1（activeRoomRef.current !== msg.roomId）；切换房间时 setActiveRoom() 清空。历史加载用 hist- 前缀 id 与流式消息合并，避免覆盖正在滚动的内容。
// chat.chunk 处理片段（useChatSocket.ts）
const key = `${msg.roomId}:${msg.messageId}`;
const isNew = !streamingRef.current.has(key);
const existing = streamingRef.current.get(key) || '';
streamingRef.current.set(key, existing + msg.content);
// 新 assistant 消息到达且不在当前房间 → 未读 +1
if (isNew && activeRoomRef.current !== msg.roomId) {
  setUnread((u) => ({ ...u, [msg.roomId]: (u[msg.roomId] || 0) + 1 }));
}
连接细节：URL 用 ${protocol}//${window.location.host}/ws（生产走 Nginx 反代，同源）；断线后 3 秒自动重连；crypto.randomUUID 在 http 域名不可用，用 getRandomValues 手写 UUID v4 兜底 —— 都是真实踩过的坑。
WS 流式时序：chat.send → thinking → chunk×N → memory → done；前端一边打字机渲染一边统计未读。

Workspace：视图切换（导航范式）

Workspace.tsx 用 activeNav state 决定主区渲染哪个组件；docView 是文档中心的二级状态（列表 ↔ 详情）。切换板块时重置 docView，保证"切走再回来"从列表开始。聊天视图还内嵌了 CreateGroupModal（创建群聊弹窗，勾选成员）与轻提示 toast（规划位点击用）。

// Workspace.tsx 的核心分发
{activeNav === 'cloud-space' ? (<CloudSpacePage />)
 : activeNav === 'knowledge' ? (<RAGLabPage />)
 : activeNav === 'docs' ? (docView ? <DocDetailPage /> : <DocsCenterPage />)
 : activeNav === 'members' ? (<MemberManagement />)
 : /* ... 其他板块 ... */
 : (<Sidebar /> + <ChatCanvas />)}   {/* 默认聊天视图 */}
设计意图：把"未来能力"直接设计成导航位（日历/任务/设置），新功能接入时只需加一个 RailItem + 一个视图分支 —— 架构上为扩展留好了槽位，这也是产品思维（飞书/微信式左侧功能列）的体现。

文档中心：Shadow DOM + TOC

文档中心是本项目"面向学习"理念的落地：12 篇学习文档以独立 HTML 文件存在后端 backend/app/docs/content/，前端负责展示。

DocsCenterPage：分类卡片

DocsCenterPage.tsx 请求 GET /api/docs/categories（后端扫描 content 目录、解析 doc:* meta 并按 category 分组），把每篇文档渲染成卡片：图标来自 meta.icon 字符串 → lucide 组件映射（ICON_MAP），分类配色来自 CATEGORY_STYLE（入门靛蓝 / 架构紫 / 核心能力翠绿 / 进阶琥珀 / 工程与部署玫红），卡片 hover 上浮 + 显示"阅读文档"。

DocDetailPage：Shadow DOM 隔离渲染

为什么用 Shadow DOM？文档自带完整样式（<style> 主题 + 组件类），直接注入页面会污染 App 的 Tailwind 样式。方案：

  1. fetch /api/docs/{docId} 拿到 doc.html 原文。
  2. 用正则把 <style>...</style> 与 <body> 内容分别抠出来，拼成 <style>{styles}</style>{body} 注入 host.attachShadow({mode:'open'}) —— 文档样式只作用于文档自身，与 App 完全隔离。
  3. React StrictMode 下组件可能二次执行，因此先 host.innerHTML='' 并 shadowRoot.replaceChildren() 清空旧内容再挂载。

手写 TOC 提取 + 滚动高亮 + 平滑跳转

  • TOC 提取：文档内的 <nav class="doc-toc"> 是手写的（不是自动生成），前端 querySelectorAll('nav.doc-toc a[href^="#"]') 读出来，用 doc-toc-h(\d) 类名解析层级（h2/h3/h4），渲染到左侧目录栏。
  • 滚动高亮：IntersectionObserver 监听每个目标 section，rootMargin: '-15% 0px -78% 0px'（只看视口顶部带状区域），多个可见时取 boundingClientRect.top 最靠上的 → setActive('#id')。
  • 跳转：点目录 → shadowRoot.querySelector(href).scrollIntoView({behavior:'smooth'})。
文档详情渲染管线：请求 → Shadow DOM 注入 → 手写 TOC 提取 → IntersectionObserver 滚动高亮与平滑跳转。

部署拓扑：双容器

部署是 Docker Compose 双容器（docker-compose.yml）：chat-server（Python FastAPI :8000）负责全部业务；web（Nginx）负责托管前端静态产物 + 反向代理 API 与 WebSocket。本地跑在 OrbStack，通过 dev.orbstack.domains 标签获得两个域名：web.aicumi.orb.local 与 chat-server.aicumi.orb.local。

chat-server 容器

  • 构建：backend/Dockerfile；暴露 8000:8000，环境变量 HOST/PORT。
  • 热更新卷：./backend/app:/app/app —— 后端代码挂在容器内，改代码即生效（开发友好）。
  • 持久化卷：./backend/data:/app/data —— SQLite（aicumi.db）、主密钥（.master_key）、ChromaDB（memory/）、云空间（cloud-space/）全部落在这里，容器重建不丢。
  • 资源与日志：mem_limit: 512m；json-file 日志 10m×3 轮转。

web 容器（多阶段构建）

# frontend/Dockerfile —— 两阶段
FROM node:20-alpine AS builder          # 阶段一：构建
RUN corepack enable && corepack prepare pnpm@10.23.0 --activate
COPY frontend/package.json frontend/pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile
COPY frontend/ .
RUN pnpm build                           # tsc -b && vite build → dist

FROM nginx:alpine                        # 阶段二：运行
COPY --from=builder /app/dist /usr/share/nginx/html
COPY frontend/nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
双容器拓扑：浏览器 → web（Nginx 静态 + 反代）→ chat-server（FastAPI + AG2），数据全部落在 host 挂载卷。

Nginx 反代细节

frontend/nginx.conf 只有 38 行，但每个 location 都有讲究：

# 静态资源：Vite 产物带内容哈希，可以放心缓存一年
location /assets/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}

# API 反代 → chat-server（透传真实 IP 与协议）
location /api/ {
    proxy_pass http://chat-server:8000/api/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# WebSocket 反代：必须 Upgrade/Connection + 超长读超时
location /ws {
    proxy_pass http://chat-server:8000/ws;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 86400;   # 24h：流式对话可长时间挂起
}

# SPA fallback：前端路由（如 /demo）都回 index.html
location / {
    try_files $uri $uri/ /index.html;
}
  • /assets 缓存一年：Vite 构建出的文件名带内容哈希（如 index-abc123.js），内容变了文件名就变，因此可以 immutable 长缓存 —— 浏览器回访零请求。
  • /ws 的 86400 读超时：默认 Nginx 代理 60s 无数据就断连，流式对话（思考可能十几秒没 token）会被误杀。设 24h + HTTP/1.1 Upgrade，是 WS 反代的标准三件套。
  • SPA fallback：try_files 把不存在的路径（前端路由）落到 /index.html，刷新不 404。

维度做了什么业内参照评分差距与改进
