五层 MAS 架构改造

多智能体协作体系 · 2026-08-26 当日完成 · 6 个提交全通过真实模型端到端验收 ｜ 建议先读 02 · 架构总览
一句话总结：AiCumi 从「多个单 Agent 并排」（业界称 multi-washing）升级为按业界五层标准体系实现的完整多智能体系统（MAS）——团队认知、群聊协调、组织编排、共享记忆、A2A 互操作。这不是补丁式修复，而是当初选型 AG2 时最想要的 GroupChat 编排能力真正落地。

为什么做：从「孤立」到「体系」

触发点：使用中发现「员工彼此不知道对方」——问可灵「小研在做什么？」，可灵回答「没有找到相关信息」。

定性：经业界调研确认，这不是单点 Bug，而是多智能体系统五层标准架构的系统性缺失。根因是三层隔离：

层面代码位置问题
人设层agent_manager.py _build_agent_instance()system_message 只含自己的人设，无团队信息
记忆层vector_memory.py search()按 agent_id 硬过滤，记忆完全私有
群聊层GroupChatManager.stream_send()被 @ 的成员各自独立回复同一条消息，彼此看不到对方输出
项目当初选 AG2 的核心理由——GroupChat 编排能力——此前从未真正使用，只是把多个 AssistantAgent 并排放着。这正是「选对了框架、没用上框架」的典型。

五层体系总览

业界把多智能体「相互认知与协作」拆解为五个子问题，每层有标准方案与代表框架。AiCumi 按此体系完整落地：

五层体系：L1 是地基 → L2 依赖 L1（选人靠角色描述）→ L3 依赖 L2 → L4/L5 相对独立。

Phase 1 · 团队认知（花名册注入）

业界做法：所有框架标配。Agent 的「同事认知」是显式注入的结构化上下文，不是模型涌现。

改造前：每个 Agent 的 system_message = 自己的人设 + 工具准则，可灵不知道小研/小码的存在。

改造后：每个 Agent 的 system_message 自动附加「团队通讯录」章节——全部在职成员的名字、角色、职责一句话、专长工具；排除自己；成员入职/离职/改名/改角色时全员实例自动重建。

文件改动
backend/app/agents/team_context.py（新建）build_roster(exclude_agent_id) 从 AgentManager 元数据生成花名册文本；缓存 + 失效机制
backend/app/agents/agent_manager.py_build_agent_instance() 注入花名册；成员变更后触发全员重建
验收通过：问可灵「小研是做什么的？」→ 准确回答「小研是调研专员，擅长 web_search…」（此前：没有找到相关信息），并主动提出可协调任务给同事。

面试叙事：「Agent 的相互认知不是涌现的，是我工程化构造的上下文，并且维护了失效一致性。」

Phase 2 · 群聊协调（SelectorGroupChat）

业界做法：AG2/AutoGen 的招牌能力 GroupChat + Speaker Selection。

改造前：被 @ 的成员并行独立回复同一条消息，彼此看不到对方输出，无发言顺序、无讨论轮次。

改造后：群聊房间按需构建 SelectorGroupChat 实例（participants = 房间成员，各带自己的 model client）。

  • 无 @：LLM 选人机制根据成员角色描述决定谁先回应、是否需要第二人补充；
  • 有 @：通过 selector_func 强制被 @ 成员先发言，后续轮次交给 LLM 选人；
  • 终止条件：MaxMessageTermination（轮次上限）+ 所有被 @ 成员已响应即收敛；
  • 流式兼容：每个成员发言仍是独立 message bubble、token 级流式（chunk 事件穿透 run_stream()）——前端协议不变。
文件改动
backend/app/agents/group_engine.py（新建）封装 SelectorGroupChat 构建/复用、selector_func(@路由)、终止条件、事件流 → (agent_id, chunk, message_id) 适配器
backend/app/agents/agent_manager.pyGroupChatManager.stream_send/send_message 内部改为调用 group_engine
验收通过：无 @ 发「产品复盘怎么分工」→ 可灵列表格 → 小研认领并引用分工表 → 可灵收尾，三轮自动调度。

面试叙事：「我用 SelectorGroupChat 实现了基于角色描述的自动发言调度，并用 selector_func 扩展点实现了产品级 @路由。」

Phase 3 · 组织编排（委派 + 主管）

业界做法：Supervisor（主管路由）与 Handoff（平级移交）是 2025 年生产环境两大主流编排模式。

3a · Handoff 委派工具

每个 Agent 注册 delegate_to_colleague(target, question) 工具（走 tool_registry），运行时可向指定同事发起子对话并取回结果，以自己的口吻转述给用户。委派动作写入 tracing（delegate 事件类型），可在追踪页观察调用链。用 ContextVar 做递归深度上限（2 层）防死循环。

验收通过：「帮我问问小码 GIL」→ 可灵委派 → 转述原话，tracing 可见完整调用链。

3b · Supervisor 主管模式

群房间支持 mode: "supervisor"——由 owner（如可灵）接收消息、分析任务、@指派合适成员、汇总结论。与自由讨论模式并存，建群时可选。supervisor 的 selector_func：owner 总是先发言，owner 通过 @id: 标记指定下一位发言者。

验收通过：「做竞品分析」→ 可灵拆解指派 → 小研调研 → 小码技术补充 → 汇总报告，完整闭环。

面试叙事：「我实现了两种主流编排模式的对比：中心化 Supervisor 路由 vs 去中心化 Handoff 委派，并能讲清各自的成本与失控风险。」

Phase 4 · 共享记忆（私有/团队）

业界做法：MetaGPT 消息池 / LangGraph 共享 State / CrewAI crew 级 Knowledge。私有+共享分层是标准形态。

改造前：记忆检索 where 条件硬编码 agent_id = 当前成员，小研调研过的东西可灵完全不知道。

改造后：记忆元数据增加 scope 字段（private 默认 / team）；检索先查私有记忆，不足时补充团队共享记忆并标注来源成员（如「来自小研的记忆」）；设置页提供开关。

文件改动
backend/app/memory/vector_memory.pyadd() 支持 scope 入库 metadata；search() 支持 include_team 合并查询（ChromaDB where $or）
backend/app/agents/agent_manager.pyretrieve_memories/build_memory_context 传 include_team 开关；enriched context 标注来源成员
backend/app/settings/router.py全局配置项 team_memory_enabled
验收通过：小研的 team 记忆被可灵跨成员检索命中，标注 source=小研。

面试叙事：「我设计了私有/团队两级记忆作用域，检索时合并并溯源标注。」

Phase 5 · A2A 互操作协议

业界做法：A2A（Google 发起，2025-06 捐赠 Linux Foundation，50+ 企业共建）是智能体互操作的事实标准。Agent Card 即「相互认知」的协议化表达。

改造前：AiCumi 的员工只能在本平台内被访问，外部世界不可见。

改造后：实现 A2A 最小服务面（原生 FastAPI，不引重依赖）：

  • GET /.well-known/agent-card.json：全团队成员的能力名片（名字、角色、技能、工具列表）；
  • 单成员粒度 Agent Card：/api/a2a/{agent_id}/.well-known/agent-card.json；
  • POST /api/a2a/{agent_id}/tasks/send：符合 A2A Task 生命周期的最小任务接口（submitted → working → completed，返回 Message/Artifact 结构）；
  • 复用现有 AgentManager.send_message 作为执行后端。
验收通过：curl /.well-known/agent-card.json 即可发现团队；外部可向小研提交任务拿到 completed 状态 + Artifact。

面试叙事：「我的平台不仅内部多智能体协作，还实现了 A2A 协议对外暴露，支持跨系统智能体发现与委托。」

群聊无 @⚠️ 仅房主响应✅ LLM 按角色描述智能调度发言人与轮次

额外收获：存量 Bug 修复

改造过程中挖出并修复了一个存量 Bug：启动时默认模型误选了 embedding 配置（qwen3.7-text-embedding），意味着小研和小码此前一直在用 embedding 模型跑对话——只是被可灵的独立模型绑定掩盖了。这正是「端到端真实验收」的价值：不跑真实对话，永远发现不了这类「不报错但悄悄不生效」的问题。
