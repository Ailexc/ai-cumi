RAG 是什么：检索增强生成

RAG（Retrieval-Augmented Generation，检索增强生成）是解决 LLM「幻觉」与「知识过期」两大问题的标准范式：模型本身不知道你的私有文档，那就先把文档变成可检索的知识库，回答问题时先把相关知识检索出来，注入 Prompt，再让模型基于这些材料生成 —— 让模型"开卷考试"而不是"闭卷编造"。

一句话原理

回答 = LLM( 用户问题 + 检索到的相关文档片段 )。四个环节缺一不可：知识库（建）→ 检索（取）→ 注入（拼）→ 生成（答）。

为什么能降低幻觉

  • 事实接地（grounding）：回答必须基于注入的片段，模型不再"自由发挥"——Prompt 里明确要求"上下文中没有相关信息请说明"。
  • 知识实时性：重新索引一次文档，知识库就"更新"了，不需要重训模型。
  • 可溯源：每个片段都带来源（文件名 + 路径），回答可以引用、可以被验证。
RAG 全链路：上半条是离线索引（文档 → 向量库），下半条是在线问答（提问 → 检索 → 注入 → 生成）。两条线由向量库串起来。
学习要点：RAG 的难点从来不是"调一个 Embedding API"，而是解析质量、分块粒度、检索召回与阈值调优四个环节的配合 —— 本篇后续逐环拆解。

云空间文件管理

云空间是 RAG 的语料来源：一个本地文件系统目录（backend/data/cloud-space/），通过 REST API 暴露文件树 / 上传 / 删除 / 建文件夹 / 搜索，并支持多格式只读预览（Markdown / 代码 / PDF / 图片）。

文件服务层

核心实现是 backend/app/cloud_space/file_service.py，全部操作基于 Path 完成：

  • list_directory()：列目录（目录在前，按名称排序）；build_tree()：递归构建整棵文件树（前端左侧树）。
  • create_folder() / save_upload() / delete_path()：建目录、写文件（shutil.copyfileobj）、删除（文件 unlink，目录 rmtree，禁止删根）。
  • 安全边界：_resolve_path() 用 Path.resolve() 后校验 str(target).startswith(str(root))，防止 ../ 穿越出云空间根目录；router 层 _safe_path() 再剥离前导斜杠并拒绝含 .. 的路径。

文档解析：多格式提取

解析器 backend/app/knowledge/parser.py 提供统一的 DocumentParser.parse(file_path, mime_type) 入口，按扩展名分派到四个解析器，产出统一的 ParsedDocument(content, metadata, page_contents)：

格式依赖库实现函数要点
Markdown / 文本 / 代码标准库_parse_text()utf-8 读取，errors="replace" 兜底乱码；代码文件也能进知识库
PDFpymupdf（fitz）_parse_pdf()逐页 page.get_text()，保留 page_contents（按页粒度），metadata 记 page_count
DOCXpython-docx_parse_docx()提取非空段落 p.text，metadata 记 paragraph_count
HTMLbeautifulsoup4_parse_html()先 decompose() 掉 script/style，再 get_text(separator="\n") 并清洗空行
设计取舍：解析器返回纯文本 + 结构化 metadata，不保留排版 —— 对 RAG 检索来说"语义"比"样式"重要；分页信息（PDF）单独存 page_contents，为未来"按页引用"留了扩展位。

分块策略与调参

一个文档常常几千字，不能整体向量化（超限、语义被稀释），必须切成有独立语义的小块。分块器 backend/app/knowledge/chunker.py 提供三种策略（TextChunker(strategy, chunk_size=512, overlap=128, separator="\n\n")）：

三种策略的差异

策略原理典型场景弱点
fixed 固定长度滑动窗口：step = chunk_size - overlap，从 0 开始等长切无结构文档、快速验证可能从句子中间切断，语义断裂
recursive 递归切分分隔符级联：\n\n → \n → 。 → ！ → ？ → . → 空格 → 字符，逐层降级，单块过长再递归通用文本（默认策略）对 Markdown 标题结构无感知
markdown 标题层级正则 ^(#{1,3}\s+.+)$ 找标题，以标题为边界切块，保留标题行结构化文档（README / 手册）无标题时回退 recursive
semantic 语义分块占位实现，目前回退 recursive（规划中）真正的语义分块需要 Embedding，留作扩展点

调参直觉（chunk_size / chunk_overlap）

  • chunk_size 太大（如 2048）：单块信息多但语义杂，检索精度下降，还可能塞爆上下文。
  • chunk_size 太小（如 128）：上下文碎片化，检索到的片段"答不全"。
  • chunk_overlap 的作用：两块之间保留尾部 overlap 字符（recursive 是 buffer[-overlap:]），避免一句话被硬生生切成两半导致两边都"读不懂"。
  • RAG 实验室里两者的滑块范围是 chunk_size 256-2048、chunk_overlap 0-256，可以实时对比检索效果。
三种分块策略的切分直觉：fixed 滑动窗口重叠、recursive 分隔符级联降级、markdown 以标题为天然边界。

Embedding 适配：千问 DashScope

Embedding 把"文本"变成"向量"（语义坐标），让相似文本在向量空间里距离更近。本项目默认使用千问 DashScope 向量模型 qwen3.7-text-embedding（1024 维），适配层在 backend/app/knowledge/embedding_provider.py，抽象基类 EmbeddingProvider 只要求两个方法：embed(texts) -> List[List[float]] 与 dimensions()。

与 OpenAI 格式的差异（重点）

维度OpenAI 兼容格式DashScope 格式（本项目默认）
请求体{"model": m, "input": ["t1","t2"]}{"model": m, "input": {"texts": ["t1","t2"]}} —— input 是对象不是数组！
响应resp.data[] 顺序与入参一致output.embeddings[] 带 text_index 字段，必须按 text_index 排序
URLPOST /v1/embeddingsPOST /api/v1/services/embeddings/text-embedding/text-embedding（专用服务端点）
维度1536 / 3072 等1024（DashScopeEmbeddingProvider.dimensions() 固定返回）

正因为格式不同，_is_dashscope_model() 通过 provider == "dashscope"、"dashscope" in base_url、"qwen" in model_name 三路判定走哪条实现（见 backend/app/knowledge/indexer.py）。

Local 哈希 fallback

没有配置任何 Embedding 模型 / 密钥时，_get_embedding_provider() 会回退到 LocalEmbeddingProvider：把文本分词后按 md5(token) % dim 投到 256 维稀疏向量并归一化。它没有语义，但能让整条 RAG 链路在没有外部 API 的情况下跑通（学习/演示模式），替换成真实模型时无需改任何调用方代码 —— 这就是抽象基类 EmbeddingProvider 的价值。

检索：向量 / 关键词 / 混合 RRF

检索器 backend/app/knowledge/retriever.py 提供三种模式（retrieval_mode: vector | keyword | hybrid），统一返回 RetrievalResult(chunk_id, content, file_name, file_path, score, chunk_index, document_id)。

三种检索方式

模式实现评分强项 / 弱项
vector 向量_vector_search()：query 向量化 → ChromaDB collection.query（n = k×2 多取候选）余弦距离转相似度：score = max(0, 1 - dist)理解语义同义改写；但对精确术语（型号/代码）不敏感
keyword 关键词_keyword_search()：collection.get(limit=2000) 拉候选 → 词频打分（BM25 近似）命中词数归一化：min(1.0, 命中数 / 词数)精确匹配强；但召回粗（全库扫描 2000 条）
hybrid 混合两路各取 k×2 → _rrf_fusion() 融合RRF：score += 1 / (k + rank + 1)（k=60），再按最大值归一化到 0..1兼顾语义与精确匹配；业界标配

RRF 融合为什么有效

RRF（Reciprocal Rank Fusion）的核心思想：不看绝对分，看排名。同一片段在向量路排第 2、在关键词路排第 5，融合分就是 1/(60+2) + 1/(60+5) ≈ 0.0169；而只在单路排第 1 的片段只有 1/61 ≈ 0.0164。两路都靠前的片段一定赢 —— 因为它被两种信号同时认可。融合后 score = 融合分 / max(融合分) 归一化到 0..1，才能让 score_threshold（默认 0.5）正常工作。

# _rrf_fusion()（retriever.py）
k = 60
for results in result_lists:
    for rank, r in enumerate(results):
        scores[r.chunk_id] = scores.get(r.chunk_id, 0.0) + 1.0 / (k + rank + 1)
max_score = max(scores.values()) if scores else 1.0
for cid, r in metas.items():
    r.score = scores[cid] / max_score          # 归一化，阈值才有效
return sorted(metas.values(), key=lambda x: x.score, reverse=True)
三种检索模式：向量看语义、关键词看精确、混合用 RRF 融合两路排名，再统一阈值过滤。
另外还有一个可选开关 rerank_enabled：_simple_rerank() 会在融合后按"关键词命中密度"给片段 +0.05 × hits 的加分（封顶 1.0）再重排 —— 这是"轻量 Rerank"的教学替代品，真正生产级会用 Cohere/Jina 的交叉编码器 Rerank 模型。

ChromaDB 索引管理

向量库选型 ChromaDB（嵌入式 PersistentClient），持久化目录 data/memory，集合名 knowledge_chunks，距离度量 {"hnsw:space": "cosine"}。索引器 backend/app/knowledge/indexer.py 负责增删改查与全量重建。

写入一条文档的完整流程（index_file）

  1. 生成 doc_id = "doc_" + uuid4().hex[:12]，先插入 KnowledgeDocument 行（status=indexing）。
  2. parser.parse() 提取全文 → chunker.chunk() 切块。
  3. provider.embed(texts) 批量向量化（DashScope 自动分批 25）。
  4. 每个 chunk 的 metadata 记录 document_id / file_path / file_name / chunk_index / chunk_strategy / chunk_size / start_char / end_char —— 检索结果的"来源"全靠这些字段。
  5. ChromaDB collection.add() 每批 100 条写入；成功置 status=indexed + chunk_count，异常置 failed + error_message[:500]。

删除与全量重建

  • delete_document(doc_id)：collection.delete(where={"document_id": doc_id}) 删向量 + 删 knowledge_documents 行。
  • delete_by_path(relative_path)：按 file_path 查到 doc 再删 —— 云空间删除文件时自动调用。
  • reindex-all（/api/knowledge/reindex-all）：先 client.delete_collection() 整个集合删掉重建（换分块参数后旧 chunk 全作废），再清空 knowledge_documents 表，最后遍历云空间把支持的扩展名（md/txt/pdf/docx/html）逐个重新索引。这是 RAG 实验室"重新索引全部"按钮的后端实现。

knowledge_documents 表

定义在 backend/app/models/__init__.py 的 KnowledgeDocument：file_path（唯一）、file_name、file_size、mime_type、chunk_count、status（pending/indexing/indexed/failed/outdated）、error_message、last_indexed_at。它是"文档 ↔ 向量"的登记表，get_stats() 据此统计已索引/失败/总 chunk 数。

局限提示：目前是"全量重建"式更新 —— 没有做增量 diff（文件改了只重索引这一个）。换参数后的 reindex-all 在大知识库上会比较慢，这是生产化时要优化的点（按 mtime 增量）。

Agent 集成与引用溯源

RAG 的最后一公里：检索结果怎么喂给 AG2 Agent。入口在 backend/app/main.py，REST（/api/chat/send）与 WS（/ws 的 chat.send）两条路都支持，共用同一个 KnowledgeScope 协议：

class KnowledgeScope(BaseModel):
    """Knowledge scope for RAG injection."""
    mode: str = "auto"          # auto | selected
    directory_ids: Optional[List[str]] = None

检索与注入（_build_rag_context）

_build_rag_context(db, query, scope) 做四件事：读 RAG 配置（get_rag_settings）→ 取 Embedding provider（_get_embedding_provider）→ 构造 KnowledgeRetriever → 按 scope 检索。其中 mode == "selected" 时用 where_filter = {"file_path": {"$in": directory_ids}} 把检索范围限定在指定目录（即"只在这批文档里找"）。

# 片段拼接（main.py）
parts.append(f"[文档片段 {i+1}] 来源: {r.file_name} ({r.file_path})\n{r.content}")
# 注入模板
user_message = (
    f"请基于以下知识库上下文回答问题。如果上下文中没有相关信息，请说明。\n\n"
    f"[知识库上下文]\n{rag_context}\n\n"
    f"[用户问题]\n{message.content}"
)

引用溯源设计

  • 每个片段自带 [文档片段 N] 来源: 文件名 (相对路径) 前缀 —— 模型可以明确引用"根据文档片段 2"。
  • Prompt 明确要求"没有相关信息就说没有"，从机制上抑制编造。
  • 前端 RAG 实验室的检索测试结果卡片直接展示 file_name + file_path + score，方便肉眼验证召回质量。
学习要点：这里体现了"协议先行"的思想 —— knowledge_scope 在 REST 与 WS 协议层都定义好了（前端 Composer 的 scope 选择器是产品层后续工作），后端链路已完全打通。

调参闭环
