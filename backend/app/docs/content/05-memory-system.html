为什么需要长期记忆

没有记忆的 Agent 是一条金鱼：每一次对话都从零开始，永远记不住五分钟前你告诉过它的事。想象一下——你上周告诉助理"我女儿叫小雨，今年 6 岁"，今天问它"我女儿多大了"，它却一脸茫然。这在 IM 场景下是不可接受的，因为用户默认"我们一直在聊天，你应该记得"。

🐠 金鱼问题的本质

  • 上下文窗口 ≠ 长期记忆：LLM 的 context window（如 128K tokens）只是"短期工作记忆"，每次调用都重新传入、用完即弃。
  • 窗口是有限的：多轮对话 + 工具结果 + RAG 片段很快撑爆窗口，还要做截断或压缩。
  • 窗口是"每问必建"的：历史消息是前端加载后拼进 prompt 的，关掉窗口再开就全丢了。

长期记忆要解决的是：把「值得记住的」从海量对话里抽出来，跨会话、按语义检索回来，在需要的时候注入 prompt。AiCumi 的记忆系统围绕四个目标设计：

  1. 自动写入：每轮对话结束自动存档（user + assistant 各一条），用户零操作。
  2. 语义检索：用 Embedding 做向量相似度匹配，而不是简单关键词——"我女儿多大了"能命中"女儿 6 岁"。
  3. 按 Agent 隔离：每个员工（agent_id）拥有自己的记忆，互不串台。
  4. 透明可管理：检索到的记忆通过 chat.memory 事件展示给前端，用户能看到"AI 记了/用了什么"。
学习要点：记忆系统是 Agent 面试的必问点。能讲清「存储层（向量库）→ 写入策略（什么该记）→ 检索注入（怎么用）→ 遗忘策略（什么该忘）」四层，就超过大多数候选人。

架构：ChromaDB 与 VectorMemory

记忆系统的核心是一个 ChromaDB 嵌入式向量库（零额外容器，数据持久化到 data/memory 目录）+ 一个统一封装类 VectorMemory。它对外暴露 add / search / get_by_agent / delete / clear / stats 六个方法，上层（AgentManager、REST API）只跟这个类打交道，不感知底层是 ChromaDB 还是内存降级。

记忆双链路：上半是「写入」——对话消息 → 分条 → 向量化 → ChromaDB；下半是「检索」——新消息 → 语义搜索 + metadata 过滤 → top-k 注入 prompt。两条链共享同一个向量库。

MemoryEntry 数据结构

一条记忆是一个 MemoryEntry dataclass（backend/app/memory/vector_memory.py），字段设计决定了"能过滤什么、能展示什么"：

字段类型说明
idstruuid4 生成，作为 ChromaDB 的 id 与前端删除句柄
contentstr记忆原文（用户消息或助手回复）
agent_idstr所属员工，记忆隔离的第一维度
memory_typestr记忆类型：conversation / fact / preference / task
metadataDict扩展属性（如 role=user），平铺进 ChromaDB metadata 供过滤
created_at / updated_atstrISO 时间戳，历史排序与展示
embeddingList[float]向量本身，仅内存态持有，不落 ChromaDB 文档字段

collection 设计与 metadata 过滤

ChromaDB 侧的设计很朴素但实用：一个 collection 装所有人的记忆，靠 metadata 过滤实现隔离，而不是每人一个 collection（那样 collection 数量会爆炸）。

# backend/app/memory/vector_memory.py · VectorMemory.__init__ / _init_chromadb
self._client = chromadb.PersistentClient(
    path=self.persist_dir,                      # data/memory，进程重启不丢
    settings=Settings(anonymized_telemetry=False),
)
self._collection = self._client.get_or_create_collection(
    name=self.collection_name,                  # "agent_memory"
    metadata={"hnsw:space": "cosine"},          # 余弦相似度空间
)
# add() 时把过滤字段写进 metadata
self._collection.add(
    ids=[entry.id], documents=[content], embeddings=[embedding],
    metadatas=[{"agent_id": agent_id, "memory_type": memory_type,
                "created_at": entry.created_at, **(metadata or {})}],
)
# search() 时用 where 过滤
where_filter = {}
if agent_id:   where_filter["agent_id"] = agent_id
if memory_type:where_filter["memory_type"] = memory_type
results = self._collection.query(
    query_embeddings=[query_embedding], n_results=n_results,
    where=where_filter if where_filter else None,
)

memory_type 维度（设计预留）

  • conversation：对话原文，当前唯一实际写入的类型
  • fact：抽取出的客观事实（"女儿 6 岁"）
  • preference：用户偏好（"喜欢简洁回答"）
  • task：任务状态（"待办 X 进行中"）

为什么是"单 collection + 过滤"

  • N 个 Agent 只需 1 个 collection，管理简单
  • ChromaDB where 支持等值过滤，检索时先过滤再算相似度
  • 未来按类型检索（只看偏好）可直接复用 memory_type 过滤
注意双写策略：add() 写入 ChromaDB 的同时，总会追加一份到进程内 _in_memory_store；get_by_agent() 会合并两个来源并按 id 去重。这让"ChromaDB 不可用/本地哈希 Embedding"时记忆依然可见——降级不是坏了，而是换一种更笨的方式工作。

对话自动存取

记忆不是靠用户手动添加，而是挂在聊天主链路上自动完成。入口在 backend/app/agents/agent_manager.py，三个方法形成闭环：save_exchange（写）→ retrieve_memories / build_memory_context（读）。

写入：save_exchange

每轮对话结束后调用，用户消息与助手回复各存一条（都用 conversation 类型，用 metadata.role 区分身份）：

# backend/app/agents/agent_manager.py · save_exchange
async def save_exchange(self, agent_id, user_message, assistant_reply):
    if not self.memory_enabled:
        return
    from ..memory import vector_memory
    if user_message and user_message.strip():
        await asyncio.to_thread(
            vector_memory.add, user_message, agent_id, "conversation",
            {"role": "user"},
        )
    if assistant_reply and assistant_reply.strip():
        await asyncio.to_thread(
            vector_memory.add, assistant_reply, agent_id, "conversation",
            {"role": "assistant"},
        )
这里有个值得讲的取舍：原文即记忆，没有做摘要/抽取。优点是无损、零额外模型调用；缺点是噪声多、检索精度受限于 Embedding。业界（MemGPT）会做"回忆压缩"，这是本项目列在"差距与改进"里的第一项。

检索：build_memory_context

发送消息前，build_memory_context 先用 retrieve_memories 做向量检索，命中则把记忆格式化拼进消息前面，作为上下文喂给模型。注意 asyncio.to_thread：ChromaDB 是同步库，放进线程池避免阻塞事件循环——这是 Python async 项目接同步库的标准姿势。

# backend/app/agents/agent_manager.py · retrieve_memories / build_memory_context
results = await asyncio.to_thread(
    vector_memory.search, query=message, agent_id=agent_id, n_results=n_results,
)
# 命中则构造"记忆上下文 + 当前消息"
lines = [f"- （{m['memory_type']}）{m['content']}" for m in memories]
context = (
    "以下是长期记忆中与当前话题相关的信息，供你参考：\n"
    + "\n".join(lines)
    + "\n\n【当前用户消息】\n"
    + message
)

__MEMORY__ 哨兵与前端展示

流式场景下，stream_message 在吐出第一个 token 之前，先 yield 一个 __MEMORY__:<json> 哨兵行，携带检索到的记忆列表。WS 处理器把它翻译成 chat.memory 事件推给前端，前端在气泡上渲染"记忆徽章"（frontend/src/components/workspace/MessageBubble.tsx）——用户能直观看到 AI 用了哪些记忆。

对话自动存取闭环：检索（读）在回复前，写入（存）在回复后——先"想起"再"回答"，答完"记下"，下次"想起"。
记忆开关：AgentManager.memory_enabled 控制整个记忆链路的启停；关闭时 build_memory_context 直接返回原消息、save_exchange 直接 return，对上层完全透明。

记忆管理 API

后端暴露一组 REST 端点（backend/app/main.py），前端在成员管理页的「记忆」标签（frontend/src/components/workspace/MemberManagement.tsx 的 MemoryView）调用，支持查看、搜索、手动添加与清空。

stats() 是理解系统健康度的入口，返回字段恰好对应三个"可用性维度"：

# backend/app/memory/vector_memory.py · stats
{
  "chromadb_available": True,      # 向量库是否可用
  "embedding_available": True,     # 是否有外部 Embedding（否则走本地哈希）
  "chromadb_count": 128,           # 向量库条数
  "in_memory_count": 128,          # 进程内备份条数
  "persist_dir": "data/memory",
  "embedding_model": "text-embedding-3-small",
}
面试可讲点：clear(agent_id) 支持按员工清空；clear(None) 则删除整个 collection 再重建——用"重建代替清空"避免残留索引状态。

Embedding 与降级链

向量记忆的命脉是 Embedding。AiCumi 设计了一条三级降级链，保证任何环境下记忆系统都能跑：

  1. 模型配置中心：优先取 model_service.get_default_embedding()（统一配置中心的 Embedding 模型 + 解密后的 key）。
  2. 环境变量：无配置时回退 OPENAI_API_KEY / OPENAI_BASE_URL（OpenAI 兼容端点）。
  3. 本地哈希 Embedding：什么都没有时，用 _local_embedding() 做确定性降级——不依赖任何外部服务。
两条降级链：Embedding 三级（配置 → 环境变量 → 本地哈希）；检索两级（向量 → 关键词）。降级保证「功能永不缺席」，代价是精度。

_local_embedding 的原理值得展开——它是典型的确定性词袋哈希向量：

# backend/app/memory/vector_memory.py · _local_embedding（要点摘录）
vec = [0.0] * dim                                  # 256 维
for tok in re.findall(r"[\w\u4e00-\u9fff]+", (text or "").lower()):
    h = int(hashlib.md5(tok.encode("utf-8")).hexdigest(), 16)
    idx = h % dim                                  # 词 → 固定桶
    sign = 1.0 if (h >> 16) & 1 else -1.0          # 词 → 正负号
    vec[idx] += sign
norm = math.sqrt(sum(v * v for v in vec)) or 1.0
return [v / norm for v in vec]                     # L2 归一化
  • 中文按 \u4e00-\u9fff 切词（re.findall 按连续字符块切，非分词器），英文按单词。
  • 每个词通过 md5 哈希映射到固定桶并带上符号，相同文本永远得到相同向量——所以能持久化到 ChromaDB 且可复现。
  • L2 归一化后余弦相似度 ≈ 点积，词重叠越多越相似——本质是"带权关键词匹配"。
  • 局限：无语义泛化（"女儿"与"孩子"不同桶），仅作兜底。
工程启示：降级不是可选项而是必选项。真实环境里 Embedding 服务可能限流/欠费/断网，向量库可能损坏——一条优雅的降级链让系统"带伤运行"而不是"整体瘫痪"，这在面试里是很好的系统设计谈资。

对比评分：LangGraph / MemGPT

业内参照：LangGraph Checkpointer（会话状态持久化 + 消息列表，无语义检索）与 MemGPT（分层记忆：核心/工作/存档，带记忆压缩与召回）。评分原则：功能完整性 × 实现深度 × 工程化 × 生产就绪度，1-5 星。

维度本项目做了什么业内参照评分差距与改进
持久化 ChromaDB PersistentClient 落盘 data/memory，进程重启不丢；内存双写兜底 LangGraph Checkpointer（SQLite/PG 后端） 4.0 ★ 单机够用；无副本/备份策略，多实例共享需独立向量服务
语义检索 向量 Embedding + cosine 近邻 + agent_id/memory_type metadata 过滤 + 关键词兜底 MemGPT 分层召回 / 混合检索 3.8 ★ 链路完整；缺 Rerank、时间衰减权重、"记忆-消息"分层（MemGPT 的核心）
自动写入 save_exchange 每轮自动存 user+assistant 两条，挂在聊天主链路，零人工 MemGPT 事件驱动写入 4.0 ★ 原文即记忆、无去重/合并；相邻轮次重复信息会堆积（需写入压缩）
遗忘策略 仅提供手动 delete / clear；无自动遗忘与重要性评分 MemGPT 存储层级 + 驱逐 2.5 ★ 最大短板：缺记忆重要性打分、自动压缩、过期淘汰；可加"合并相似记忆"后台任务
总体：记忆闭环（写 → 存 → 检 → 注入 → 展示）真实完整，3.6 / 5.0。与 LangGraph Checkpointer（偏"状态快照"）相比，本项目是真正的"语义记忆"；与 MemGPT 相比，缺分层与遗忘。改进路线清晰：写入压缩（LLM 摘要）→ 记忆评分 → 自动合并。

学习路径

  1. 先跑通 VectorMemory：单测里 add → search 一条记忆，观察返回结构与相似度排序。
  2. 追 stream_message：看 __MEMORY__ 哨兵何时 yield、WS 层如何翻译成 chat.memory。
  3. 关掉模型配置中心再看 stats()：确认 embedding_available=False 时系统仍可用——降级链生效。
  4. 读 save_exchange 的调用点（消息收尾处），理解"写发生在回复之后"。
  5. 自问三个面试题：为什么用单 collection + metadata 过滤？为什么 asyncio.to_thread？遗忘策略怎么补？
一句话总结：记忆 = 向量库存储 + 对话自动写入 + top-k 语义注入 + 三级降级保底，并通过 chat.memory 把"AI 记了什么"透明地交还用户。
